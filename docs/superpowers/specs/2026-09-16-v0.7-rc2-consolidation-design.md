# Coding Tools v0.7.0-rc.2 Consolidation Design

## Objective

Consolidate the approved Coding Tools MCP work onto one release-candidate lineage derived from the published `v0.7.0-rc.1` source. The result must expose provider, subagent, orchestrator, Paseo, Anneal, proxy, Traditional Chinese, OAuth-compatibility, and release controls through coherent contracts without replaying stale branches over newer fixes.

## Source and preservation rules

- Consolidation branch: `integration/v0.7.0-rc.2-all-project-work`.
- Source baseline: the current Provider Center and Anneal orchestrator head, which is itself based on `v0.7.0-rc.1`.
- Historical branches, tags, releases, workflow evidence, and user-authored files are preserved.
- No file is deleted. Replaced retained material belongs under `Trash/`; temporary scripts, generated evidence, and validation artifacts belong under `aiTemp/`.
- Stale pull requests are closed only after their behavior is proven present, superseded, or safely ported.
- Provider credentials remain outside bundled application source and release artifacts.

## Architecture

### Provider Center

A normalized provider registry owns provider identity, category, authentication kind, protocol, capabilities, health, model discovery, priority, and admission into Paseo or Anneal. Built-in surfaces include API-key providers, Codex OAuth, Claude OAuth, ChatGPT Web, AI Studio Reverse Proxy, Gemini Reverse Proxy, AIStudioToAPI, CLIProxyAPI/Antigravity, CommandCode Proxy, and user-defined compatible providers.

Provider definitions must be data-driven. The GUI reads the same registry contracts used by routing and orchestration; it must not maintain an unrelated hard-coded provider list. Secrets are represented only by secure references or connection state, never serialized into ordinary profile exports.

### Subagents

A subagent profile selects a provider/model pair, role, required capabilities, tool grants, permission policy, enabled state, and bounded execution settings. The registry supports built-in and user-defined profiles. An orchestrator profile may be exposed as a subagent so a parent workflow can delegate a bounded child task to another workflow.

Paseo resolves eligible subagents from the registry. Resolution rejects disabled profiles, missing capabilities, unavailable providers, recursion, and workflows that exceed the parent task's permission or execution budget.

### Custom orchestrators

Anneal remains the task supervisor and scheduler. The custom orchestrator editor produces structured Anneal-compatible plans rather than a second independent scheduler. A workflow contains ordered stages, per-stage agent/provider/model selection, fallback targets, retry limits, approval policy, completion conditions, timeout/budget limits, and failure transitions.

Before dispatch, the GUI presents the resolved execution plan. Runtime state records stage status, observations, retries, selected agent/provider, evidence, and terminal reason. Cyclic orchestration is rejected unless represented by an explicitly bounded retry/fallback rule.

### Anneal monitoring and web tasks

Anneal receives bounded observations from chat/task state, GitHub status, build/test status, browser state, and custom web tasks. Completion is never inferred from a single phrase alone: declared completion rules may require a combination such as task-output evidence plus a successful build, merged pull request, published release, or verified browser state.

Custom web tasks are declarative sequences of allowed actions such as navigation, extraction, assertion, and approved interaction. Each task specifies origin allowlists, credential mode, action limits, timeout, evidence capture, and success/failure conditions. Web tasks use existing browser safety and permission boundaries; they do not silently bypass approval or expose session material.

### Proxy and localization

Proxy configuration is represented by typed routing and IPC contracts so selected application traffic can use a user-configured proxy without embedding credentials. Provider traffic, browser traffic, and local-loopback traffic remain distinguishable; local control endpoints must not be accidentally routed externally.

Traditional Chinese is a first-class locale backed by the same localization keys as English. New Provider, Agent, Orchestrator, Task, Monitor, and proxy controls must not rely on untranslated inline text.

### OAuth compatibility

Port the verified RFC 9207 authorization-response issuer behavior and RFC 9728 MCP protected-resource metadata behavior from the combined validation branch onto the v0.7 source. The port must preserve both invariants:

1. The trusted public issuer is validated before consent or authorization-code state is mutated, and a successful callback contains exactly one server-controlled `iss` value.
2. The path-derived protected-resource metadata identifies the exact `/mcp` resource and the bearer challenge advertises the matching discovery location.

Only the verified focused files are ported. Token, refresh, confidential-client, redirect-allowlist, and release behavior are not broadened as part of this port.

## Integration sequence

1. Start from the current Provider Center/Anneal structured-orchestrator head.
2. Integrate the subagent/orchestrator continuation through an isolated pull request.
3. Integrate proxy, orchestration IPC, provider contracts, and Traditional Chinese through an isolated pull request.
4. Port the combined OAuth issuer/RFC 9728 behavior with focused regression contracts.
5. Audit remaining v0.6 and legacy PRs; port only changes not already superseded by v0.7.
6. Run exact-source frontend, TypeScript, Node, Rust, release-contract, no-delete, package-content, and packaged-launcher checks.
7. Produce the rc.2 Windows x64 installer only from the tested source SHA, with checksum, provenance, and validation evidence.
8. Promote to `main` only after the rc.2 integration PR and release gate are green.

## Error handling and safety

- Missing provider, model, capability, consent, or secure credential reference fails closed with an actionable status.
- Provider and web failures are bounded by stage retry and fallback rules; unbounded loops are prohibited.
- Anneal marks ambiguous completion as `verifying` or `blocked`, never `completed`.
- Browser and external-network tasks retain origin and permission checks.
- OAuth invalid-issuer handling must not consume one-time consent or create an unreachable code.
- Release publication remains fail-closed if build, package, smoke, checksum, provenance, or source-identity verification fails.

## Acceptance criteria

- Provider profiles, selectable subagents, and custom orchestrators share typed runtime contracts and persistent configuration.
- A custom orchestrator can be selected as a bounded subagent without recursive self-dispatch.
- Anneal can evaluate declared completion rules using chat/task, GitHub, build, browser, and custom-web observations.
- Proxy and Traditional Chinese contracts are wired into the release-candidate source rather than existing only as detached type files.
- RFC 9207 issuer and RFC 9728 `/mcp` metadata regressions pass on the consolidated head.
- Existing `/goal`, native/Web routing, compaction, OAuth persistence, Paseo/Anneal execution, package smoke, and no-delete behavior do not regress.
- The exact tested source produces a verified Windows x64 installer and release evidence before promotion to `main`.

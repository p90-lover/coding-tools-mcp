# AI／人類協作流程與學習指南

**繁體中文** · [English](ai-human-workflow.en.md) · [產品說明](../../README.md)

本指南描述 `v0.4.1-rc.1` 的使用流程，是一套工作方法，不代表程式會自主運行工程團隊或訓練模型。哪些項目已經測試，應以實際公開版本的驗證紀錄為準。

## 三個角色

**人類**負責目標、授權範圍、驗收條件及發佈決定；**AI 用戶端**閱讀上下文、提出修改、選擇可用工具並解釋結果；**Coding Tools MCP**負責本機工具執行、權限檢查、結果回傳及專案歷史機制。程式不會偷偷啟動另一輪 Codex 推論或 AI 審查員。

```text
人類目標＋限制
  → 專案指示＋有界歷史
  → 小範圍計劃＋驗收檢查
  → 按最新權限批准
  → 本機檔案／命令／圖片／電腦工具
  → 實際結果與證據
  → 人類審查／修正
  → 已驗證檢查點與經驗
  → 明確批准交付
```

回饋有兩條路：檢查失敗便返回調查並修訂假設；需求不清楚便返回人類確認，而不是猜測實作。輸入結果不明時，先重新觀察；不能只因回應逾時，就重播已送出的點擊、命令或外部操作。

## 1. 行動前先定義成功

例子：「變更權限時不用重啟或重新連接 MCP；截圖只留在記憶體；保留所有檔案；不要呼叫 Codex 推論；提供 Windows 安裝程式。」

可驗收的條件包括：同一個監聽服務與憑證繼續有效；唯讀時拒絕寫入，在本機改變權限後容許寫入；舊批准不能授權新操作；撤銷截圖權限後，丟棄尚在處理的畫面；原始碼身分、安裝程式版本及校驗碼一致。這些是待驗證條件，不是預設成立的事實。

先確定受保護檔案、允許目錄、命令能否連接網絡，以及哪些操作須另行取得人類批准。臨時工作放在 `aiTemp/`，不需要的檔案保留於 `Trash/`。程式的 `policy_only` 命令執行器並不是全面的作業系統沙箱或刪除攔截器。

## 2. 恢復上下文，而不是一次載入全部歷史

先查看 `server_info`、`codex_tools_status` 及專案指示。需要保存精確起始要求時，以使用者逐字的 `initial_user_input` 呼叫 `history_session_bootstrap`，保留回傳的 `session_key` 及 `current_path`。

若用戶端提供 `_meta.openai/session`，伺服器可在一般呼叫時自動建立或恢復相應的有界檔案；這不代表它能讀取用戶端未提供的對話。較早的細節先用 `history_session_search` 搜尋，再按回傳游標與預期雜湊，以 `history_session_read` 分頁讀取。不要捏造缺失歷史，也不要把舊的「通過」報告當成現行證據。

## 3. 計劃保持小而明確

短期工作計劃先呼叫 `get_plan`，再把回傳修訂版放入 `update_plan`：

```json
{
  "expected_revision": 0,
  "explanation": "先重現，再修改權限路徑。",
  "plan": [
    {"step": "重現目前行為", "status": "in_progress"},
    {"step": "作出最小範圍修正", "status": "pending"},
    {"step": "驗證並審查結果", "status": "pending"}
  ]
}
```

請把 `0` 換成 `get_plan` 實際回傳的修訂版。同一時間最多只有一個步驟進行中。計劃保存在該監聽服務的記憶體、由其共用，服務退出便消失；它不會執行任務。需要長期保留的審查紀錄，應使用專案 Markdown／歷史或本機看板。

看板的十二階段為：規格、計劃、計劃審查、修訂計劃、實作、程式碼審查、獨立審查、套用修正、文件、驗證、合併準備、交付。記錄某個階段，是由操作者以筆記支持的陳述，不是審查員或測試實際執行的證明。沒有呼叫 AI 審查員時，不能把「獨立審查」歸功於不存在的審查。

## 4. 先檢查、再操作、然後驗證

優先使用結構化介面：修改前先讀取／搜尋程式碼，視需要檢查 Git 及執行 Patch 預檢。桌面操作先考慮已知應用程式能力或 UI Automation 選擇器，才使用座標輸入；需要座標時，使用新截圖及精確的目標身分。

背景**觀察**不等於背景**輸入**。已批准、受支援的視窗可在不啟用前台的情況下觀察；真實 Windows 鍵鼠輸入仍需要指定目標位於前台。「持續啟用」表示本機批准沒有倒數，不代表批准所有視窗或持續上傳截圖。請保持暫停／停止控制可見。

只選擇針對改動風險的檢查。以上權限例子最值得驗證的是：同一個已認證服務上的請求流程、授權／撤銷行為，以及安裝程式身分。修改電腦操作時，還要執行隔離的真實 Windows 鍵鼠／截圖測試。保留實際結果，包括失敗；樂觀摘要不是證據。

## 5. 把審查變成學習

執行前，人類先預測結果並解釋理由；AI 說明正在檢查哪個假設、最小有用檢查，以及甚麼結果會推翻該假設。執行後，再比較預測與觀察，解釋差異。

可使用的審查問題是：「指出修改的界線、保留了甚麼行為，以及哪些地方仍未測試。」要求原始碼及測試證據，而非模型的私密推理。若人類尚未理解變更到足以維護，就不應接受；AI 亦應在證據不符時修訂提案，而非把失敗重新包裝成成功。

簡短的經驗範本：

```markdown
## 經驗：<具體而可重用的主題>
背景及範圍：
觀察到的症狀：
初步假設：
預期結果：
執行的檢查及精確環境：
實際結果／證據位置：
被否定的解釋：
已確認原因或仍存在的疑問：
最小修正：
回歸風險及後續檢查：
人類審查決定與理由：
可重用規則及其適用界線：
```

不要放入機密、認證標頭、完整私人對話或截圖；改為連結非敏感的證據紀錄。明確區分「已觀察」、「推斷」及「未驗證」。

## 6. 儲存交接並批准交付

任務結束時，以已保存的 `session_key` 呼叫 `history_session_checkpoint`，把原先回傳的 `current_path` 作為 `expected_path`，並以 `raw_user_input` 傳入使用者的逐字要求。只有確認 `ok=true` 且目標一致後，才能表示進度已儲存。新對話應恢復該目標，而非另開不相關檔案。

發佈決定要分開記錄：原始碼已提交、檢查通過、安裝程式已建置、套件已檢查、檔案已上傳、版本已公開，以及 main 已更新。不能因只有一個 Commit 或 CI 正在運行，就宣稱七項全部完成。有效交接須附精確 Commit、改變的行為、實際執行的檢查、剩餘限制及真正的檔案連結。

## 這裡的「學習」是甚麼意思

**人類學習：** 比較預測與結果，並解釋經審查的修改，可找出理解上的缺口。**AI 任務適應：** 下次會話可重新讀取已批准的筆記及專案指示，作為上下文。**未實作：** 自動更新模型權重、微調、跨帳戶全域記憶，或以你的截圖訓練模型。本機計劃、看板與歷史的保存期限不同，不應混為一談。

期望改善的是減少重複解釋、明確記錄不確定性、縮小差異及簡化交接；它們是設計目標，不是效能測試結論。可量度重複回歸、審查返工、不明結果重試，以及重建上下文所花時間。把舊經驗變成永久專案規則前，先重新審查；某個程式適用的規則，未必適用於另一個程式。

## 工具與整合限制

用 `tool_search` 及 `codex_tools_status` 核對能力，不要假設每個 Codex 內部處理器都可用。本機命令／檔案／修補／計劃／圖片對應功能，不代表包含 Codex 子 Agent、上下文視窗管理、雲端搜尋或帳戶／外掛 API。對話提問仍留在 AI 用戶端；原生命令沙箱未納入，一般命令仍是 `policy_only`。

Paseo／Anneal 介接器只觀察已存在的本機服務，未內嵌或啟動其完整語音／手機、排程、Agent 審查及自主合併引擎。外部服務可能自行消耗供應商配額；本程式的本機工具及本次發佈流程不會呼叫 Codex 推論。

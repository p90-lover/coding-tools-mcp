# v0.4.6 — Load-resilient MCP traces and safer tunnel recovery

## English

The user reported mid-task tool disablement without changing the connector and noticed a lagging PC. Resource contention can delay a local response, but the message "tool has been disabled" is not proof of a CPU/disk fault. This release fixes two reproduced application weaknesses; it does not claim to reproduce or override ChatGPT's disabled state, change app eligibility, or guarantee continuous service on an overloaded computer.

**MCP trace logging no longer performs disk writes on the request/execution thread.** The released handler previously called the synchronous log sink before admitting even a protocol ping. A controlled 800-ms sink delay reproduced an async scheduler stall. The new MCP-only diagnostic queue uses one dedicated writer, at most 256 queued entries plus the active write, a 4 KiB line cap, and bounded destination identifiers. Enqueue is nonblocking with respect to storage. Overflow and shortened traces are counted; a writer creation failure does not fall back to blocking the request. The task monitor exposes process-wide diagnostic backlog/drop counters. These counters are not CPU utilization, disk utilization or task completion measurements.

Tradeoff: diagnostic traces are explicitly best effort. A full queue can omit lines, and queued traces can be lost on process exit. The existing disk sink can still fail silently, so "processed" is not a durability acknowledgement. The authoritative runtime-local operation store is unchanged: it records completion independently of trace persistence. Missing log lines are not evidence of nonexecution; inspect operation/task handles rather than replaying work. This patch does not bound existing log-file disk size, change other logging paths, remove all synchronous I/O from the application, or make RAM-only receipts durable over restart.

**A transient Windows ownership-query error no longer permanently blocks tunnel recovery.** The previous recovery check collapsed errors into "local runtime not owned", requiring manual start indefinitely. Now an unsuccessful query defers that tick without starting a child or consuming a restart attempt. A successful lookup showing a different/missing listener still blocks recovery. Original Stop behavior, ownership enforcement, configuration checks, five-attempt crash-recovery cap, OAuth secrets and endpoint handling are retained. This repair is not a new endless reconnect loop or a reason to restart a healthy listener after 408.

The focused tests cover actual handler behavior under a controlled slow trace sink, bounded/nonblocking trace queuing, and the actual recovery ownership-decision branch with failed/successful OS-query fixtures. Native Windows build and existing real OAuth, protocol-control, live-permission, linked-root, task-monitor and AppContainer gates run separately. Fixture measurements are not benchmarks of the user's PC, Cloudflare or ChatGPT. No live training/game operation, Codex/model inference, connector recreation or deletion command is executed.

Quick Tunnel remains supported with its existing limitations. Local recovery cannot force ChatGPT to re-enable a tool, update a client URL after hostname rotation, or keep a browser conversation executing forever. Unknown in-flight operations must be reconciled before upgrading because current operation receipts are memory-only. Preserve configuration, extension v0.0.7 and the old executable. The Windows x64 installer is publisher-unsigned; publishing does not silently replace the user's running Desktop. Full Paseo/Anneal execution integration remains on its separate branch and is not claimed complete here.

## 繁體中文

使用者表示沒有改動連接器，但工具在任務途中被停用，且電腦當時卡頓。資源競爭可能拖慢本機回應，但「tool has been disabled」不能證明一定是 CPU／磁碟問題。本版本修正兩個已重現的程式弱點，不會宣稱已重現或能覆寫 ChatGPT 的停用狀態、改變 App 使用資格，亦不保證過載電腦上的服務永不中斷。

**MCP 追蹤日誌不再在請求／執行執行緒直接寫入磁碟。** 舊 handler 在接受協定 ping 前也會呼叫同步日誌；以 800 ms 寫入延遲測試時，已重現非同步排程被拖住。新的 MCP 專用診斷佇列使用一個獨立寫入執行緒，最多 256 項等待及一項進行中的寫入，每行最多 4 KiB，目的地識別資料亦有上限。加入佇列不等待磁碟，溢出及截短會計數；無法建立 writer 時也不會退回阻塞請求。任務監察可顯示整個程序的診斷積壓／省略數量，但這不是 CPU、磁碟使用率或任務完成度。

取捨：診斷日誌是盡力記錄，不是持久化工作憑據。佇列滿時可能省略日誌，程序退出時未寫出內容可能遺失。現有磁碟 sink 仍可能靜默失敗，因此 processed 不等於已持久儲存。真正操作狀態儲存保持不變，完成紀錄獨立於診斷日誌。缺少日誌不代表從未執行，須查原有 operation／task handle，不要重新派發。本次沒有改變既有日誌檔案大小上限、其他日誌路徑，也不代表已移除程式全部同步 I/O 或令記憶體操作紀錄跨重啟保留。

**Windows 查詢端口擁有者短暫出錯時，不再永久阻止隧道恢復。** 舊邏輯把查詢錯誤當成「本機 runtime 不屬於自己」，之後一直要求手動啟動。現在會略過該輪，不啟動子程序也不消耗重啟次數；成功查詢但發現 listener 缺失或屬於別的程序時，仍阻止恢復。保留 Stop、擁有權、設定檢查、最多五次崩潰恢復、OAuth 密鑰及端點處理。這不是無限重連，也不會因為 408 就重啟健康 listener。

集中測試包含真正 handler 在模擬慢日誌下的行為、有界非阻塞佇列，以及真正恢復邏輯在 OS 查詢成功／失敗時的分支。Windows 原生建置與既有 OAuth、協定控制、即時權限、linked root、任務監察及 AppContainer 另行驗證。測試數字不是使用者電腦、Cloudflare 或 ChatGPT 的效能測量；不執行真實訓練／遊戲、Codex／模型推論、重建連接器或刪除指令。

Quick Tunnel 保持支援及原有限制。本機恢復不能強迫 ChatGPT 重新啟用工具、在 hostname 變更後自動改寫用戶端 URL，或令瀏覽器對話永遠運行。升級前先確認結果未知的操作，因為目前操作紀錄只存在記憶體。保留設定、擴充功能 v0.0.7 及舊執行檔。Windows x64 installer 沒有發行者簽章，公開發佈不代表已替換使用者正在運行的 Desktop。完整 Paseo／Anneal 執行整合仍在獨立分支，本版不宣稱已全部完成。

# v0.4.4-rc.2 — MCP timeout recovery

## English

Adds `mcp_operation_status` for inspecting accepted MCP HTTP requests without running them again. The worker, not the HTTP waiter, owns completion recording. A disconnected/timed-out waiter no longer suppresses the worker's completion receipt. Each admitted request receives a unique operation ID in `X-MCP-Operation-Id` and response metadata (or error data). At the 105-second application wait deadline, HTTP 408 includes the operation ID, query arguments, `execution_cancelled:false` and `safe_to_retry:false`. The existing 120-second outer guard, authentication and Origin policy remain unchanged. A client/gateway may time out earlier; use the original request ID or recent receipts in that case. This is recoverable outcome tracking, not a promise to eliminate all timeouts.

After refreshing the client's tool list, call `mcp_operation_status` with `{"operation_id":"<returned id>","include_result":true}`. To find a receipt, use `{"request_id":123}` with the ORIGINAL JSON-RPC id and its original string/integer type, or `{}` for the latest 10 records. Lookup is read-only, has four reserved worker slots separate from execution admission, and does not automatically bootstrap history. It is available in Core, Read-only and Advanced/Full. The new tool has an outputSchema validated against the actual HTTP result; existing tool schemas are not represented as comprehensively rewritten.

Receipts distinguish admitted, running, completed and worker_failed. Completed means the RPC/tool dispatcher returned, NOT that a returned command/task/process has exited. Check that tool's own command/task handle next. Worker failure leaves the side-effect outcome unknown. Request IDs correlate but are NOT idempotency keys: resubmitting the same request can run it again. This release never automatically retries or claims exactly-once execution.

Results are RAM-only and scoped to the same listener's workspace/authentication authority. Different listeners, even with the same directory, do not share receipts. The existing configured bearer/OAuth credentials are still required; there is no unauthenticated result endpoint. Cached results are withheld after a live policy revision or when the original tool is no longer exposed. This is not additional per-user identity inside a shared workspace credential.

Limits: 128 records per listener, at most 256 KiB serialized cached response per operation, and a 30-minute terminal TTL. Oldest terminal receipts can be evicted sooner when the count limit is reached; active operations are not evicted. Oversized responses retain completion metadata but not the full result. No new result bodies or arguments are written to disk; existing request logs receive escaped identifiers and outcome summaries. Missing/expired/restarted records always mean UNKNOWN, never proof that execution did not happen. Results from calls made before this upgrade cannot be reconstructed. Reconcile an existing unknown operation BEFORE stopping or upgrading Desktop.

The focused regression first uses the unchanged released listener with a synthetic side effect to reproduce completion lost after an abandoned wait. Three verification groups cover retained results and no redispatch, bounded/policy-aware results and failure, and a real authenticated HTTP lookup with every ordinary execution slot occupied. The HTTP result is schema-validated. Existing OAuth/extension 0.0.7 manual and automatic consent checks, catalogue/connection checks, and AppContainer permission/native checks gate the Windows build. No Codex executable, model, live ChatGPT account, game or computer-input action is invoked. Tools now total 71: Core 58, Read-only 42, Advanced/Full 71. The previous 70 definitions, OAuth repair and opt-in native snapshot boundary remain.

Windows x64, unsigned prerelease. Original files and previous releases are preserved; temporary and backup files stay under aiTemp/Trash. Source, tag, installer and main must agree before publication. The broader Paseo/Anneal integration and incomplete branches are not silently merged. This does not verify the user's installed runtime, diagnose which original call timed out, or complete every requested integration.

## 繁體中文

新增 `mcp_operation_status`，查詢已接受的 MCP HTTP 操作而不重新執行。完成紀錄由 worker 持有，不再依賴 HTTP 等待者；連線中斷或等待逾時後，worker 完成時仍會記錄結果。每次接受請求均產生獨立 operation ID，放在 `X-MCP-Operation-Id` 及回應 metadata／錯誤資料。應用程式等待 105 秒後回傳的 HTTP 408，包含 ID、查詢參數、`execution_cancelled:false` 及 `safe_to_retry:false`。原有 120 秒外層防護、認證及 Origin 策略不變。用戶端／閘道可能更早逾時，可用原始 request ID 或最近紀錄查找。這是結果追蹤修正，不代表消除所有逾時。

更新用戶端工具清單後，以 `{"operation_id":"<回傳的 id>","include_result":true}` 呼叫 `mcp_operation_status`。查找紀錄可用 `{"request_id":123}`，須保持原始 JSON-RPC id 的字串／整數型別；或用 `{}` 取得最近 10 項。查詢為唯讀，使用獨立的四個工作名額，不會排在一般執行名額之後，也不自動建立歷史會話。Core、Read-only 及 Advanced／Full 均有此工具。新增工具提供 outputSchema，並用真正 HTTP 結果驗證；沒有把其他工具的 schema 宣稱為全部重寫完成。

紀錄區分 admitted、running、completed 及 worker_failed。Completed 只表示 RPC／工具分派已返回，不代表回傳的 command／task／process 已結束，仍須使用對應工具查其 handle。Worker 失敗時，副作用結果保持未知。Request ID 只用於關聯，不是冪等鍵；重新提交相同請求仍可能再次執行。本版本不會自動重試，也不宣稱 exactly-once 執行。

結果只存於記憶體，綁定同一 listener 的工作區及認證範圍。不同 listener 即使用相同目錄也不共用紀錄；仍須使用已設定的 Bearer／OAuth 憑證，沒有新增未認證的結果端點。即時權限版本改變，或原工具不再公開時，快取內容不會返回。共用工作區憑證內不會因此額外建立逐使用者身分邊界。

限制為每個 listener 128 項紀錄，每項完整序列化回應最多 256 KiB，已結束紀錄最多保留 30 分鐘；到達數量上限時，最舊已結束紀錄可能提早被替換，但不會移除仍在執行的紀錄。過大回應只保留完成狀態，不保留完整內容。不把新的結果本文或參數寫到磁碟，現有請求日誌只加入已跳脫的識別資料及結果摘要。查不到、已過期或重啟後的紀錄一律表示未知，不能當成從未執行。升級前的操作無法補建紀錄；停止或升級 Desktop 前，先確認現有未知操作的實際狀態。

回歸測試先使用原版 listener 與模擬副作用，重現 HTTP 等待中斷後遺失完成紀錄。三組驗證涵蓋結果保留及不重跑、容量／權限／失敗狀態，以及一般執行名額全滿時的真正認證 HTTP 查詢，並驗證結果 schema。Windows 建置仍須通過原有 OAuth／擴充功能 0.0.7 手動及自動授權、工具目錄／連線，以及 AppContainer 權限／原生檢查。沒有執行 Codex、模型、真實 ChatGPT 帳戶、遊戲或電腦輸入。工具總數為 71：Core 58、Read-only 42、Advanced／Full 71；保留原有 70 個定義、OAuth 修正及需明確同意的原生快照邊界。

提供 Windows x64 未簽章預發佈版。保留舊檔案及 Release，暫存／備份置於 aiTemp／Trash。原始碼、tag、installer 及 main 一致才公開，不暗中合併未完成的 Paseo／Anneal 或其他分支。本版本不代表已驗證使用者本機 runtime、確認原本哪個操作逾時，或完成全部整合要求。

# Coding Tools 0.8.108

## English

### Browser: Connect MCP works while the background connector setup is running (#1162)
- **Connect for all accounts could fail on every account at once.** On 2026-11-09 it was refused for all 22 accounts within 8 seconds, each with "Finish the active browser or setup operation before creating the connector."
  - The app's own background setup, which connects accounts automatically, was holding the browser. Your Connect neither waited for it nor asked it to stop, and the page went on to try every remaining account the same way.
- **Your Connect now goes first.** The background setup steps aside at its next step and tries that account again later; this is not counted as a failure.
  - Your Connect waits up to a minute for whatever is using the browser, such as a page's account check. A running Codex turn is not waited for.
- **If the browser is still busy, Connect for all accounts stops** and says so ("stopped: the browser is busy with another operation"), instead of marking each remaining account as failed. Accounts it didn't try keep their state.
- Account cards no longer show Electron's "Error invoking remote method…" prefix on an error.

### Browser: Connect MCP works on accounts with no plugins, and a failed card names the step (#1165)
- **Connect MCP never worked on an account that had never created a plugin.** ChatGPT shows such an account no Personal tab, and the setup treated the missing tab as a broken page ("ChatGPT did not expose one Personal plugins tab"). It now recognises ChatGPT's empty plugin list and goes on to Add.
  - The list must still read empty 1.5 s later, and a Personal tab that shows up late wins.
- **A request the page cancelled itself** (a tab switch, a re-render or a sign-in redirect) no longer fails the connector with "MCP ownership metadata is unavailable or exceeded its bound".
- **A failed card now names the step that stopped it**, instead of "Connector creation failed. Check Configuration in Coding Tools." About 30 of the setup's own messages used to fall through to that catch-all. An error on ChatGPT's own form says it stopped there, without repeating the page's text.

### Browser: Connect MCP no longer fails when a frame inside the page redirects (#1167)
- **Connect MCP and the workspace check could fail before connecting** when a frame embedded in the ChatGPT page redirected. The setup read the frame's redirect as the account page itself moving away, and stopped.
- **Redirects inside embedded frames are now ignored.** A redirect of the page itself is still checked as before, and so are the account, workspace, role and tunnel checks.

### Chats: agent tool calls no longer freeze the window while their paths are checked (#1160)
- **Each agent tool call with a file path checks that the path stays inside the chat's worktree.** That check read the disk on the app's main thread, and on the busy hard disk one call held every window for 0.4 s (2026-11-09).
- The check now runs off the main thread. What it allows is unchanged:
  - links are followed to their real target;
  - a link that points nowhere is refused;
  - a path that doesn't exist yet is checked through its deepest existing folder.

### Chats: page tabs float as a glass dock under your chats (#1161)
- **The page numbers (1 2 3 … +) move from the title bar to the bottom of the chat column, centred under your chats.** They sit in a frosted, see-through glass pill: light glass over the light chat, smoked glass beside a dark one.
  - A liquid bubble sits behind the open page's number. Turning a page stretches it across to the new number, then springs it into place.
  - Pointing at the dock lifts it a little and sends one gleam across it. The numbers lift when pointed at and shrink when pressed, and + turns a quarter.
  - Nothing moves on its own. With Windows' "Animation effects" off, the bubble just jumps.
- **The chat column keeps a slim strip at the bottom for the dock, so it never covers a message box,** with one chat or ten split chats. The title bar is a plain drag area again.

### Performance: the window no longer freezes for seconds because another app reads the screen (#1166)
- **Coding Tools froze for 2–4 seconds about 7 times an hour while chats were in use** (2026-11-09). In each freeze the app's main thread was busy inside Chromium itself, with none of the app's own code running.
  - The cause was Chromium's accessibility tree. Any app that reads the screen through Windows UI Automation (screen tools, overlays, automation tools, even this app's computer use) turns it on in every Chromium app, and it stays on until the app quits. Every change in a chat then became accessibility work on the main thread, although no screen reader was running.
- **It is now on only while a screen reader runs.** Coding Tools starts with it blocked. When Windows says a screen reader is running (NVDA, JAWS and Narrator say so), it turns on at once, also for a screen reader started later, and off again when the screen reader quits.
- **Settings › General › Accessibility › Screen reader support:** Automatic (the default), Always on, or Off. Always on brings back the old behaviour for every app that reads Coding Tools' window; leaving it takes effect after a restart, which the row says.
- Computer use's inspect of Coding Tools' own window now sees only the window frame unless Screen reader support is Always on.

### Updates: Update goes ahead of the background MCP connector setup (#1166)
- **Update could be refused on every click for minutes.** On 2026-11-10, 35 clicks in two minutes were each refused at once with "Wait for MCP connector creation to finish before quitting Coding Tools". The app's background setup was working through your accounts, holding the browser 15–45 seconds for each.
- **Update now goes first.** The background setup starts no new account; the one in progress gets up to a minute to finish, then the update installs. The setup carries on in the new version.
- Clicking Update again while it is being prepared joins that attempt instead of asking again.

### Computer use: permission prompts hold the agent, `computer_guide` teaches the tools, and a refused call no longer ends control (#1156)
- **An agent's computer call now waits for your answer.** The chat's tool server used to answer only at the end. An agent's MCP client then timed out while you read the per-app card ("computer_select_window … timed out"), and an Allow given later started control the agent never heard about.
  - A call still running after 2 s is answered as a stream. It carries keep-alives, or progress saying what it waits for ("Waiting for the person to allow Claude Code to use Notepad in the chat."). Faster calls are answered exactly as before.
  - The result says what you decided: allowed for this conversation, from now on, or already allowed. A refusal is `APPROVAL_DECLINED`, and the agent is told not to ask again or work around it.
  - If the agent hangs up, the card is withdrawn, and an Allow that arrives late starts nothing.
- **A new `computer_guide` tool teaches the agent the computer tools.** It covers how to observe, act by element and check the result, every Codex window method with its parameters, how to find a control, browsers, and key names, plus notes for common apps.
  - Your own Markdown notes per app go in `<userData>/computer-guides/`.
  - Choosing a window returns that app's guide, so the agent starts informed.
- **One refused call no longer ends control.** Any error from the Codex engine used to stop control (a stale element, a parameter it rejected), and the agent had to select its window again. Now it is that call's error alone (`CODEX_ACTION_REJECTED`), and control stays on.
  - Control still ends when the engine closes, when the engine's own 10-second request timer gives up (it then kills its helper), on physical Escape, or when the window is no longer the one you approved.
  - Errors name the kind of failure (`CODEX_CAPTURE_FAILED`, `CODEX_ENGINE_TIMEOUT`, …) but never the engine's own text, which can carry window titles or paths.
  - The Codex engine doesn't control ChatGPT or Codex windows. For those, snapshots fall back to an in-memory capture plus UI Automation and are marked view-only. Clicks and typing are refused as not sent, and control stays on.
  - Choosing another window moves control there instead of failing.
- **The control bar shows more.**
  - Each computer call appears as soon as it arrives, reading "… · waiting for approval" while it is reviewed.
  - The bar shows the controlled program's own icon.
  - It previews the frame the agent saw last. Nothing extra is captured for it.

### Performance: fewer freezes when Coding Tools starts and when you open your first chat (#1168)
- **Starting Coding Tools could freeze every window for 5.6 seconds** (0.8.106, 2026-11-10). Each time the app started its bridge or checked it, it confirmed on the main thread that the bundled runtime's files exist, although startup had just checked every file of that runtime in the background. A runtime checked that way is now trusted; one nobody has checked is still checked once.
- **The first chat after each start froze the window for about a second** while it read your saved subagents and MCP servers. Both are now read in the background as the app starts.
- **Starting CPA froze the window for about half a second** while it looked for a waiting CPA update. That record is now read in the background, as the periodic update check already did.

### Updates: a CPA update no longer freezes the app (#1169)
- **Installing a CPA update could freeze every window for seconds.** On 0.8.106 (2026-11-10), the CPA 8.0.63 update held the app's main thread for up to 2.5 s at a time while it created folders, moved files and checked the download's SHA-256.
- **A CPA update now downloads, checks and installs the new version in the background**, without freezing the app.

## 繁體中文

### 瀏覽器：背景連接器設定執行時也能「連接 MCP」（#1162）
- **「連接所有帳戶」可能讓每個帳戶同時失敗。** 2026-11-09 時，22 個帳戶在 8 秒內全部被拒，每個都顯示「Finish the active browser or setup operation before creating the connector.」
  - 原因是應用程式自動連接帳戶的背景設定正佔用瀏覽器。你的連接既不等待它，也不要求它停止，頁面還會以同樣方式繼續嘗試其餘每個帳戶。
- **現在你的連接優先。** 背景設定會在下一步讓開，稍後再為該帳戶重試，這不算失敗。
  - 你的連接最多等待一分鐘，讓正在使用瀏覽器的作業（例如頁面的帳戶檢查）結束。不會等待正在執行的 Codex 回合。
- **若瀏覽器仍然忙碌，「連接所有帳戶」會停下並說明原因**（「stopped: the browser is busy with another operation」），而不是把其餘每個帳戶都標為失敗。未嘗試的帳戶維持原狀。
- 帳戶卡片上的錯誤不再帶有 Electron 的「Error invoking remote method…」前綴。

### 瀏覽器：沒有外掛的帳戶也能「連接 MCP」，失敗的卡片會指出停在哪一步（#1165）
- **從未建立過外掛的帳戶，以前永遠無法「連接 MCP」。** ChatGPT 不會為這類帳戶顯示「個人」分頁，而設定流程把缺少分頁當成頁面損壞（「ChatGPT did not expose one Personal plugins tab」）。現在它能辨認 ChatGPT 的空外掛清單，並繼續執行「新增」。
  - 清單在 1.5 秒後仍須是空的；稍後才出現的「個人」分頁優先。
- **頁面自行取消的請求**（切換分頁、重新繪製或登入重新導向）不再讓連接器以「MCP ownership metadata is unavailable or exceeded its bound」失敗。
- **失敗的卡片現在會指出停在哪一步**，而不再顯示「Connector creation failed. Check Configuration in Coding Tools.」設定流程約 30 則自身訊息過去都落入這個通用訊息。ChatGPT 表單本身的錯誤會說明停在該處，但不會照抄頁面文字。

### 瀏覽器：頁面內的框架重新導向時，「連接 MCP」不再失敗（#1167）
- **ChatGPT 頁面內嵌的框架重新導向時，「連接 MCP」與工作區檢查可能在連接前就失敗。** 設定流程把框架的重新導向當成帳戶頁面本身離開，因而停止。
- **現在會忽略內嵌框架中的重新導向。** 頁面本身的重新導向仍照舊檢查，帳戶、工作區、角色與通道的檢查也都不變。

### 對話：檢查代理工具呼叫的路徑時不再凍結視窗（#1160）
- **每個帶有檔案路徑的代理工具呼叫，都會檢查路徑是否仍在對話的工作樹內。** 這項檢查原本在應用程式主執行緒上讀取磁碟；在忙碌的硬碟上，一次呼叫曾讓所有視窗停住 0.4 秒（2026-11-09）。
- 這項檢查現在在主執行緒之外執行。允許的範圍不變：
  - 連結會追到實際目標；
  - 指向不存在之處的連結會被拒絕；
  - 尚不存在的路徑，會以其最深的現有資料夾檢查。

### 對話：頁籤改為浮在對話下方的玻璃列（#1161）
- **頁碼（1 2 3 … +）從標題列移到對話欄底部，置中於對話下方。** 頁碼放在一個磨砂、半透明的玻璃膠囊中：淺色對話上是淺色玻璃，深色對話旁是煙燻玻璃。
  - 目前頁碼後方有一顆液態氣泡。換頁時，它會伸展到新的頁碼，再彈回定位。
  - 指標移到玻璃列上時，它會微微升起，並有一道光掃過。頁碼在指向時會升起、按下時會縮小，+ 會轉四分之一圈。
  - 沒有任何東西會自行持續動作。若關閉 Windows 的「動畫效果」，氣泡會直接跳到新位置。
- **對話欄底部保留一條窄帶給玻璃列，因此它不會遮住訊息框，** 無論是單一對話或十個分割對話。標題列恢復為單純的拖曳區域。

### 效能：不再因其他程式讀取螢幕而凍結數秒（#1166）
- **使用對話時，Coding Tools 每小時約凍結 7 次，每次 2–4 秒**（2026-11-09）。每次凍結時，應用程式的主執行緒都忙於 Chromium 本身，沒有執行任何應用程式自己的程式碼。
  - 原因是 Chromium 的無障礙樹。任何透過 Windows UI Automation 讀取螢幕的程式（螢幕工具、疊加層、自動化工具，甚至本程式的電腦操作）都會在所有 Chromium 程式中開啟它，並一直開著直到程式結束。之後對話中的每個變更都會在主執行緒上產生無障礙工作，即使並沒有執行螢幕閱讀器。
- **現在只有在螢幕閱讀器執行時才會開啟。** Coding Tools 啟動時會先封鎖它。當 Windows 表示有螢幕閱讀器正在執行（NVDA、JAWS 與 Narrator 都會告知），它會立即開啟，之後才啟動的螢幕閱讀器也一樣；螢幕閱讀器結束時會再關閉。
- **Settings › General › Accessibility › Screen reader support：** Automatic（預設）、Always on 或 Off。Always on 會恢復舊行為，讓所有讀取 Coding Tools 視窗的程式都能讀取；從 Always on 改回要在重新啟動後才生效，該列會說明。
- 除非 Screen reader support 設為 Always on，電腦操作的 inspect 對 Coding Tools 自己的視窗只會看到視窗框架。

### 更新：Update 優先於背景 MCP 連接器設定（#1166）
- **Update 可能在數分鐘內每次點擊都被拒絕。** 2026-11-10 時，兩分鐘內 35 次點擊都立即被拒，顯示「Wait for MCP connector creation to finish before quitting Coding Tools」。當時應用程式的背景設定正逐一處理你的帳戶，每個帳戶佔用瀏覽器 15–45 秒。
- **現在 Update 優先。** 背景設定不再開始新的帳戶；進行中的帳戶最多有一分鐘完成，之後便安裝更新。背景設定會在新版本中繼續。
- 準備更新期間再次點擊 Update，會加入同一次嘗試，而不會再詢問一次。

### 電腦操作：權限提示會讓代理等待、`computer_guide` 教代理使用工具，單一被拒的呼叫不再結束控制（#1156）
- **代理的電腦操作呼叫現在會等你回答。** 對話的工具伺服器過去只在最後才回應。代理的 MCP 用戶端因此在你閱讀各程式的授權卡片時逾時（「computer_select_window … timed out」），之後才按下的「允許」會開始一段代理從不知道的控制。
  - 執行超過 2 秒的呼叫會改以串流回應，其中帶有保持連線訊號，或說明正在等待什麼的進度（「Waiting for the person to allow Claude Code to use Notepad in the chat.」）。較快的呼叫回應方式與以前完全相同。
  - 結果會說明你的決定：允許此對話、從現在起允許，或已經允許。拒絕時為 `APPROVAL_DECLINED`，並告知代理不要再詢問或設法繞過。
  - 若代理中途掛斷，卡片會撤回，之後才到的「允許」不會開始任何控制。
- **新的 `computer_guide` 工具教代理使用電腦操作工具。** 內容包括如何觀察、依元素操作並確認結果、每個 Codex 視窗方法及其參數、如何找到控制項、瀏覽器與按鍵名稱，以及常用程式的說明。
  - 你自己為各程式寫的 Markdown 說明放在 `<userData>/computer-guides/`。
  - 選擇視窗時會一併傳回該程式的說明，讓代理一開始就了解它。
- **單一被拒的呼叫不再結束控制。** 過去 Codex 引擎的任何錯誤（過期的元素、被拒的參數）都會停止控制，代理必須重新選擇視窗。現在那只是該次呼叫的錯誤（`CODEX_ACTION_REJECTED`），控制會持續。
  - 以下情況仍會結束控制：引擎關閉、引擎本身 10 秒的請求計時器放棄（此時它會結束其輔助程式）、按下實體 Escape 鍵，或視窗已不是你核准的那一個。
  - 錯誤會指出失敗類型（`CODEX_CAPTURE_FAILED`、`CODEX_ENGINE_TIMEOUT` 等），但絕不包含引擎本身的文字，因為其中可能有視窗標題或路徑。
  - Codex 引擎不控制 ChatGPT 與 Codex 視窗。對這些視窗，快照會改用記憶體內擷取加上 UI Automation，並標示為僅供檢視。點擊與輸入會以「未送出」拒絕，控制會持續。
  - 選擇另一個視窗時，控制會轉移過去，而不是失敗。
- **控制列顯示更多資訊。**
  - 每個電腦操作呼叫一到達就會顯示，審核期間顯示「… · waiting for approval」。
  - 控制列會顯示被控制程式本身的圖示。
  - 它會預覽代理最後看到的畫面，不會為此額外擷取任何畫面。

### 效能：啟動 Coding Tools 及開啟第一個對話時更少凍結（#1168）
- **啟動 Coding Tools 時，所有視窗可能凍結 5.6 秒**（0.8.106，2026-11-10）。程式每次啟動或檢查橋接器時，都會在主執行緒上確認內建執行環境的檔案是否存在，即使啟動時已在背景檢查過該執行環境的每個檔案。以這種方式檢查過的執行環境現在會直接採信；未經檢查的仍會檢查一次。
- **每次啟動後的第一個對話會讓視窗凍結約一秒**，因為要讀取你儲存的子代理與 MCP 伺服器。兩者現在都會在程式啟動時於背景讀取。
- **啟動 CPA 時會讓視窗凍結約半秒**，因為要查看是否有待套用的 CPA 更新。這份紀錄現在改在背景讀取，與定期更新檢查的做法相同。

### 更新：CPA 更新不再讓程式卡住（#1169）
- **安裝 CPA 更新時，所有視窗可能凍結數秒。** 在 0.8.106（2026-11-10）上，CPA 8.0.63 更新在建立資料夾、移動檔案與檢查下載檔的 SHA-256 時，每次讓程式主執行緒停住最多 2.5 秒。
- **現在 CPA 更新會在背景下載、檢查並安裝新版本**，不再讓程式卡住。

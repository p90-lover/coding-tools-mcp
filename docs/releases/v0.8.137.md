# Coding Tools v0.8.137

## English

### Permissions work on every harness

- **The problem.** An Antigravity chat refused Ask for approval and Approve for me with "Choose Full access". Picking Full access then failed with "IPC_TRANSPORT_FAILED: apps.call failed: Select nonempty unique known supported mission role IDs", so the chat could not run at all. Pi, opencode and Unreal Agent had no permission menu. A chat moved onto one of them lost its permission mode and showed "Custom", which ran opencode with every tool allowed.
- **Why.** The app's saved-chat store took a permission pick only on Claude Code and Codex. The launch and the menu kept separate lists that disagreed with it.
- **What changed.**
  - Full access works on every harness. It is each agent's own "skip permissions" mode.
  - Every harness shows all three modes. Ask for approval and Approve for me run on Claude Code, Codex and Native Codex. On the other harnesses they are listed with the reason they can't run:
    - Antigravity and Cline ask in their own terminal, which the chat does not show.
    - Pi and Unreal Agent never ask before running a tool.
    - opencode allows every tool by its own default.
  - A chat sent in one of those modes stops at once with that reason. It no longer waits for good, runs unchecked, or retries eight times.
  - A chat keeps its permission mode when you switch harness.
- **Context window.** The window chip now says why it's off where it can't be set. Antigravity and Unreal Agent size their own window and have no setting for it. Pi takes a window only on CPA models. Where it can be set (Claude Code, Codex, Native Codex, opencode, Pi on CPA), it works as before.
- **Not changed.** Ask for approval and Approve for me on Antigravity, opencode and Pi need their agent to hand its tool requests to the chat. That is separate work in Agent Orchestrator.

### Antigravity runs on CPA's models

- **The problem.** An Antigravity chat on Gemini 4 Carbon (High) never sent its first message. Antigravity's own log said "Your current account is not eligible for Antigravity, because it is not currently available in your location" and "Verify your account to continue".
- **Why.** The model picked was Antigravity's own, which runs on the Google account Antigravity is signed into, and Google refuses that account. It started with Antigravity 1.5.10. The same Gemini models through CPA answered.
- **What changed.**
  - Antigravity now lists only CPA's models, like Claude Code and opencode. They run through Antigravity's gateway mode, which needs no Google sign-in.
  - If CPA can't be read, the chat says so instead of offering Antigravity's own models.
  - A chat saved on one of Antigravity's own models is told to choose another before anything starts.

### CPA: the app no longer gets your own computer banned from CPA's management

- **The problem.** CPA's console showed "IP banned due to too many failed attempts. Try again in 12m32s", Auth Files listed 0 credentials, and every management call failed for 30 minutes, the app's own included.
- **Why.** CPA counts every management request with a missing or wrong key as a failed login, and bans the address after five. Every program on this computer reaches CPA from 127.0.0.1, so one ban locks out the whole machine. The app never hands its management key to the CPA console. The console gets a placeholder that the app swaps for the real key as each request leaves. A request the swap did not cover was sent anyway, and could only fail:
  - one still in flight while the console reloads or you switch pages, whose frame is gone;
  - one carrying no key, or a stored value that isn't a key;
  - one from a plugin page outside its own routes.
- **What changed.**
  - Such a request is now cancelled before it leaves the app, so it never counts toward a ban.
  - The app's log names each cancelled request by reason and path, never the key, so a repeat shows where it came from.
  - A window closing after another opened no longer removes the key swap the other window relies on.

### MCP: a chat's model lookup no longer fails Connect MCP

- **The problem.** Connect MCP failed with "Wait for the current runtime setup to finish before connecting MCP." while nothing was being set up.
- **Why.** While chats run, each one looks up the WebGPT model list through the runtime every 2 minutes, which takes about 2 seconds. Connect MCP counted that lookup as a runtime setup at every step of a setup that runs for minutes. Any overlap failed the whole Connect, and the automatic setup kept stopping to wait.
- **What changed.** The lookup only reads, so Connect MCP and the automatic setup now carry on through it.

## 繁體中文

### 每個 harness 都能使用權限設定

- **問題。** Antigravity 對話拒絕「要求核准」和「替我核准」，並提示「選擇完全存取」。但選了「完全存取」之後卻出現「IPC_TRANSPORT_FAILED: apps.call failed: Select nonempty unique known supported mission role IDs」，對話完全無法執行。Pi、opencode 和 Unreal Agent 沒有權限選單。對話切換到這些 harness 時會失去權限模式並顯示「自訂」，讓 opencode 在允許所有工具的情況下執行。
- **原因。** 應用程式儲存對話的地方只接受 Claude Code 和 Codex 的權限選擇，而啟動流程和選單各自保留了與它不一致的清單。
- **改了什麼。**
  - 「完全存取」在每個 harness 都能使用，對應各代理程式自己的「略過權限」模式。
  - 每個 harness 都會列出三種模式。「要求核准」和「替我核准」可在 Claude Code、Codex 和 Native Codex 上執行。在其他 harness 上，這兩種模式會列出無法使用的原因：
    - Antigravity 和 Cline 在自己的終端機裡詢問，對話看不到。
    - Pi 和 Unreal Agent 執行工具前從不詢問。
    - opencode 預設允許所有工具。
  - 以這些模式送出的對話會立即停止並說明原因，不會再無限等待、在無人審查下執行，或重試八次。
  - 切換 harness 時，對話會保留原本的權限模式。
- **上下文視窗。** 無法設定時，視窗按鈕現在會說明原因：Antigravity 和 Unreal Agent 會自行決定視窗大小，且沒有可調整的設定；Pi 只有在 CPA 模型上才能設定視窗。可以設定的 harness（Claude Code、Codex、Native Codex、opencode、CPA 上的 Pi）維持原本的行為。
- **沒有改變的部分。** 要讓 Antigravity、opencode 和 Pi 支援「要求核准」和「替我核准」，必須讓這些代理程式把工具請求交給對話，這是 Agent Orchestrator 中另外的工作。

### Antigravity 改用 CPA 的模型

- **問題。** 使用 Gemini 4 Carbon (High) 的 Antigravity 聊天一直沒有送出第一則訊息。Antigravity 自己的記錄寫著「Your current account is not eligible for Antigravity, because it is not currently available in your location」以及「Verify your account to continue」。
- **原因。** 選到的是 Antigravity 自己的模型，它使用 Antigravity 登入的 Google 帳號，而 Google 拒絕了這個帳號。問題從 Antigravity 1.5.10 開始。同樣的 Gemini 模型透過 CPA 則可以正常回應。
- **改了什麼。**
  - Antigravity 現在只列出 CPA 的模型，與 Claude Code 和 opencode 相同。這些模型透過 Antigravity 的閘道模式執行，不需要 Google 登入。
  - 若無法讀取 CPA，聊天會直接說明，而不是改列 Antigravity 自己的模型。
  - 儲存在 Antigravity 自有模型上的聊天，會在啟動前提示改選其他模型。

### CPA：應用程式不會再讓你自己的電腦被 CPA 管理介面封鎖

- **問題。** CPA 主控台顯示「IP banned due to too many failed attempts. Try again in 12m32s」，Auth Files 列出 0 個憑證，30 分鐘內所有管理呼叫都失敗，包括應用程式自己的呼叫。
- **原因。** CPA 會把每個缺少金鑰或金鑰錯誤的管理請求算作一次登入失敗，五次之後就封鎖該位址。這台電腦上的每個程式都是從 127.0.0.1 連到 CPA，所以一次封鎖就會鎖住整台電腦。應用程式從不把管理金鑰交給 CPA 主控台；主控台拿到的是一個佔位值，應用程式會在每個請求送出時換成真正的金鑰。沒有被替換到的請求以前還是會送出，而它只可能失敗：
  - 主控台重新載入或你切換頁面時仍在進行、框架已經消失的請求；
  - 沒有金鑰，或帶著一個不是金鑰的儲存值的請求；
  - 外掛頁面送到自己路由以外的請求。
- **改了什麼。**
  - 這類請求現在會在離開應用程式前取消，因此不會被算進封鎖次數。
  - 應用程式的記錄會依原因和路徑記下每個被取消的請求（從不記錄金鑰），所以再發生時能看出來源。
  - 一個視窗在另一個視窗開啟後關閉時，不會再移除另一個視窗所依賴的金鑰替換。

### MCP：對話的模型查詢不會再讓「Connect MCP」失敗

- **問題。** 即使沒有在進行任何設定，「Connect MCP」也會以「Wait for the current runtime setup to finish before connecting MCP.」失敗。
- **原因。** 聊天執行期間，每個聊天每 2 分鐘會透過 runtime 查詢一次 WebGPT 模型清單，每次約 2 秒。「Connect MCP」在可能長達數分鐘的設定中，每一步都把這次查詢當成 runtime 設定。只要時間重疊，整個連線就會失敗，自動設定也會一再停下等待。
- **改了什麼。** 這次查詢只會讀取資料，所以「Connect MCP」和自動設定現在都會繼續進行。

# Coding Tools 0.8.118

## English

### Freezes (#1299)
- **Less disk thrashing from the chat service (#1299).** Agent Orchestrator's cleanup of old streaming chunks no longer rereads its whole database every 15 minutes.
  - On 2026-11-13 it read 297 GB in about twelve hours from a 3.9 GB database, and kept a hard disk fully busy.
  - That busy disk caused chats that failed to resume after about three minutes, timeouts across the app (conversation pages, agent commands, CPA quota and usage), and update downloads that stalled.
  - Each cleanup pass now continues where the last one stopped, reads only the rows old enough to remove, and skips everything already cleaned. After the first pass following a start, it reads only the last day's rows.
- **Agent Orchestrator no longer retries a deleted usage transcript every 5 minutes forever (#1299, AO#42).** When a chat's transcript file was gone, AO retried reading it every 5 minutes for as long as that chat's usage record stayed open: a database write, a re-check of every watched transcript, and an Activity warning each time. Three such chats filled most of the Activity log. The retry now waits twice as long each time, up to 6 hours; a transcript that only moved is still found within about 3.5 minutes.

### Updates (#1299)
- **An update no longer fails because a file of an earlier, abandoned update is still in use (#1299).** On 2026-11-14 a retried update to 0.8.117 stopped with "EPERM: operation not permitted, unlink ...ao-daemon.exe": the earlier attempt's copy of ao-daemon.exe was still running, because Agent Orchestrator had started from it. The update now stages without it, leaves that folder for the next update, and records it in the Activity log.
- **A failed update no longer leaves Agent Orchestrator's files missing (#1299).** On 2026-11-14 the app was opened again during the update to 0.8.117, five seconds before the update began replacing files. Its start-up cleanup deleted the old copies the update keeps for undoing itself. The update then failed, and undoing it left ten files missing, ao-daemon.exe among them, so no chat could start until a later retry put them back.
  - The update now marks itself as running before the old app closes, so an app opened meanwhile waits until the files are in place.
  - The start-up cleanup skips while an update is in progress.
  - If an old copy is missing anyway, undoing the update keeps the new file instead of leaving nothing.

### Chats (#1297)
- **A message you send in a long chat no longer shows someone else's finished reply until its own reply starts (#1297).** In a chat that had compacted its history, a just-sent message showed as answered by the previous reply, with that reply's time ("Worked for 14m 30s" a minute after sending). It now shows as waiting until its own reply starts.

## 繁體中文

### 卡頓（#1299）
- **聊天服務不再大量讀取硬碟（#1299）。** Agent Orchestrator 清理舊串流片段時，不再每 15 分鐘重讀整個資料庫。
  - 2026-11-13 它在約十二小時內從 3.9 GB 的資料庫讀取了 297 GB，使硬碟持續滿載。
  - 硬碟滿載造成：聊天約三分鐘後仍無法恢復、整個 App 逾時（對話頁面、代理程式指令、CPA 額度與用量），以及更新下載停滯。
  - 每次清理現在會從上次停止處繼續，只讀取夠舊、可刪除的資料列，並略過已清理的部分。啟動後第一次清理完成之後，只會讀取最近一天的資料列。
- **Agent Orchestrator 不再每 5 分鐘無限次重試已刪除的用量記錄檔（#1299，AO#42）。** 對話的記錄檔不存在時，只要該對話的用量記錄仍未結束，AO 就會每 5 分鐘重試讀取一次：每次都寫入資料庫、重新檢查所有監看中的記錄檔，並在活動記錄留下一則警告。三個這樣的對話佔滿了大部分活動記錄。現在每次重試的間隔加倍，最長 6 小時；只是被移動的記錄檔仍會在約 3.5 分鐘內找到。

### 更新（#1299）
- **先前中斷的更新若仍有檔案被占用，不再導致更新失敗（#1299）。** 2026-11-14 重試更新至 0.8.117 時，因「EPERM: operation not permitted, unlink ...ao-daemon.exe」而中止：上一次嘗試留下的 ao-daemon.exe 副本仍在執行，因為 Agent Orchestrator 是從它啟動的。現在更新會略過該資料夾照常準備，留待下次更新再清除，並記錄在活動記錄中。
- **更新失敗時不再讓 Agent Orchestrator 的檔案遺失（#1299）。** 2026-11-14 更新至 0.8.117 期間，App 在更新開始替換檔案前五秒被再次開啟。它的啟動清理刪除了更新為復原而保留的舊副本。更新隨後失敗，復原時有十個檔案遺失（包括 ao-daemon.exe），所有對話都無法開始，直到之後重試更新才補回。
  - 更新現在會在舊 App 關閉前就標記為進行中，期間開啟的 App 會等到檔案就位。
  - 更新進行中時，啟動清理會略過。
  - 若舊副本仍然遺失，復原時會保留新檔案，而不是留下空缺。

### 對話（#1297）
- **在較長的對話中送出的訊息，在自己的回覆開始前，不再顯示為上一則回覆的結果（#1297）。** 在已壓縮歷史的對話中，剛送出的訊息會被顯示為已由上一則回覆回答，並帶著那則回覆的時間（送出一分鐘後就顯示「Worked for 14m 30s」）。現在會顯示為等待中，直到它自己的回覆開始。

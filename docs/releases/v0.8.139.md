# Coding Tools v0.8.139

## English

### Less lag while the pet naps

- **The problem.** With the app window open, its page kept a core busy even when nothing was happening, and the computer felt slow. The window drew about 93 frames a second, each repainting a 63,000-element page, and sent the graphics process about 1.3 GB a minute.
- **Why.** The pet sleeping in its cottage shows three rising "z" marks. They looped at the screen's full refresh rate, so the whole page redrew at that rate. The app already slows its other looping marks (the working shimmers, pulsing dots and spinners) to 10–30 steps a second; the pet's z's and its chimney smoke were left out.
- **What changed.** The pet's z's and smoke now step with the other marks. They look the same, and the window no longer redraws at full speed while the pet naps.

### ChatGPT browser management: an account that can't connect MCP stops retrying in the background

- Automatic MCP setup retried accounts that kept failing, and every retry loaded chatgpt.com in hidden windows. Each runtime restart wiped their wait. A restart happens on every account switch that changes the plan. So every failing account was set up again, one after another, on a machine that was already lagging.
- Now a failing account keeps its wait through a runtime restart that keeps the same MCP tunnel. Only connected accounts check their connector again.
- When ChatGPT asks an account to sign in again (a revoked sign-in or a security check), or OpenAI Platform asks it to sign in, its automatic setup waits for that sign-in. It is not tried again on a timer. It runs again once the account signs in again or signs out, or you press Connect MCP yourself. A Connect by hand that works also ends the wait.
- Other failures still wait 10 minutes, then 20 and 40, up to an hour. A refreshed sign-in cookie or a failure recorded elsewhere no longer cuts that wait short. A newly started tunnel retries only the failures it can fix.
- Switching to an account whose ChatGPT sign-in is gone no longer runs core setup or restarts the runtime. The plan update waits for that account's next sign-in.
- Setup reads its rollback copies of config.json and the other setup files without blocking the app. On the busy disk, that read had frozen every window for a quarter of a second.

### Verification

- Measured on the running 0.8.138 app, pausing only the pet's z's for 30 seconds: the page's traffic to the graphics process went from 1,345 to 438 MB a minute, the page from 95% to 80% of a core, and the graphics process from 46% to 30%.
- Giving the z's their own GPU layer instead changed nothing (1,224 MB a minute), so the cost was the frame rate they forced, not their drawing.
- New test: the napping pet's z's and smoke are paused and stepped on the shared clock. It fails on the old code. All 11 ticker tests pass.
- MCP setup: the new tests (nine automatic-setup cases and the setup-checkpoint read) fail on the old code. Of 1,656 tests in the 77 files that use the main process or the runtime, 1,640 pass. 14 couldn't load a module (Electron, Playwright, js-yaml); those 7 files pass 320 of 320 with an Electron stand-in and the shared modules.
- Everything in 0.8.138 is included.

## 繁體中文

### 寵物小睡時不再拖慢電腦

- **問題。** 開著應用程式視窗時，即使沒有任何動作，頁面仍持續佔用一個 CPU 核心，電腦感覺變慢。視窗每秒繪製約 93 個畫面，每次都重繪一個有 63,000 個元素的頁面，並每分鐘傳送約 1.3 GB 給圖形處理程序。
- **原因。** 寵物在小屋裡睡覺時會顯示三個往上飄的「z」。它們以螢幕的完整更新率循環，因此整個頁面也以這個速度重繪。應用程式原本就會把其他循環標記（工作中的閃光、跳動的圓點與轉圈）放慢到每秒 10–30 步，但寵物的 z 和煙囪的煙被漏掉了。
- **變更。** 寵物的 z 和煙現在與其他標記一起逐步更新。外觀不變，寵物小睡時視窗也不再全速重繪。

### ChatGPT 瀏覽器管理：無法連接 MCP 的帳號不再在背景反覆重試

- 自動 MCP 設定會一再重試持續失敗的帳號，每次都在隱藏視窗中載入 chatgpt.com。每次執行環境重新啟動都會清掉它們的等待時間。每次切換到不同方案的帳號都會重新啟動執行環境。所以每個失敗的帳號都會一個接一個重新設定，而電腦本來就已經很慢。
- 現在，如果重新啟動後仍是同一條 MCP 通道，失敗的帳號會繼續等待。只有已連接的帳號會再檢查它的連接器。
- 當 ChatGPT 要求帳號重新登入（登入已被撤銷或安全檢查），或 OpenAI Platform 要求它登入時，它的自動設定會等待那次登入，不會按時間重試。等帳號重新登入或登出，或你自己按下 Connect MCP 後，它才會再執行。手動連接成功也會結束等待。
- 其他失敗仍會先等 10 分鐘，然後 20、40 分鐘，最多一小時。登入 Cookie 更新或其他地方記錄的失敗，不再會縮短這段等待。新啟動的通道只會重試它能修正的失敗。
- 切換到 ChatGPT 登入已失效的帳號時，不會再執行核心設定或重新啟動執行環境。方案更新會等到該帳號下次登入。
- 設定程序在讀取 config.json 和其他設定檔的還原副本時，不會再卡住整個 App。在忙碌的硬碟上，這次讀取曾讓所有視窗凍結約四分之一秒。

### 驗證

- 在執行中的 0.8.138 上量測，只暫停寵物的 z 30 秒：頁面傳給圖形處理程序的資料由每分鐘 1,345 MB 降到 438 MB，頁面由 95% 降到 80% 個核心，圖形處理程序由 46% 降到 30%。
- 改為讓 z 擁有自己的 GPU 圖層則沒有任何改善（每分鐘 1,224 MB），所以成本來自它們強制的畫面更新率，而不是繪製本身。
- 新測試：寵物小睡時的 z 和煙會被暫停，並依共用時鐘逐步更新。此測試在舊程式碼上失敗。所有 11 項閃光計時器測試皆通過。
- MCP 設定：新測試（九個自動設定情境與設定檢查點的讀取）在舊程式碼上失敗。在使用主程序或執行環境的 77 個測試檔中，1,656 項測試有 1,640 項通過。14 項無法載入模組（Electron、Playwright、js-yaml）；這 7 個檔案在使用 Electron 替身與共用模組時，320 項全部通過。
- 包含 0.8.138 的所有內容。

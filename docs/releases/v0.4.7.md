# v0.4.7 — ordinary unbounded execution and RAM cache

This release improves the local command lifecycle and the ChatGPT/MCP polling path.
It includes the v0.4.6 nonblocking request-trace and transient-recovery fixes,
and builds on v0.4.5 and preserves its task monitor, live approved-root snapshots,
permission enforcement and fail-closed baseline admission.

## Changes

### 繁體中文摘要

一般指令不再有預設運行期限，亦不需另選「長時間模式」。省略 `timeout_ms`、傳入 null 或 0，均代表沒有自動到期時間；七天不是上限。正數時限只代表呼叫者明確要求停止的期限。HTTP 回應等待時間與程序壽命分開；手動取消、權限撤銷及程序樹管理仍然保留。

可丟棄輸出快取只存於 RAM，共用資料容量 64 MiB，每個輸出串流最多 1 MiB；資料最多保留 90 分鐘，容量不足時優先移除最舊資料。讀取不會延長到期時間；即使舊任務已運行多日，它剛產生的新輸出仍會優先保留。清快取不會刪除任務檢查點、不會停止運行中程序，亦不會釋放其寫入鎖。

這不是已完成七天實際耐久測試的聲明。伺服器重啟、作業系統終止、停電或明確取消仍會中斷程序。原始碼、認證、任務歷史、編譯產物及子程式自行管理的快取不會被當成可丟棄快取清除。RAM-only 不代表修改作業系統的分頁設定。

### Detailed changes

- Select a task's approved `project_root` and exact `task_id` per request instead of
  changing a listener-wide workspace. Independent projects can run commands at the
  same time; overlapping writers are explicitly rejected while their owned command
  is still running. Patches must stay inside one selected project.
- Ordinary `exec_command` has no automatic runtime deadline: omit `timeout_ms`, or
  pass null/0. Jobs can exceed seven days without selecting a separate mode. A
  positive caller-supplied timeout remains an explicit opt-in stop condition,
  without the former ten-minute or 24-hour cap. HTTP response waits remain short
  and independent of the job's lifetime. Poll the returned `command_id`.
- Disposable output payloads use RAM only: 64 MiB shared payload budget and 1 MiB
  per stream. Oldest payloads are evicted first, retaining the newest data even
  for a multi-day command. Chunks expire after at most 90 minutes; reading does
  not extend their age. An idle expiry worker releases allocations without a new
  request. Absolute output offsets survive expiry and capacity eviction.
- Completed command records and operation receipts use 90-minute retention and
  oldest-completed-first pressure eviction. Cache expiry never evicts active
  command ownership, cancels a job, releases its write lease, or removes a task
  checkpoint. Completion metadata is bounded separately from output payloads.
- Deliver initial stdin before returning even when `yield_time_ms` is zero. Input
  writes are bounded and reauthorized on each submission without holding a policy
  lock while waiting on a pipe. Uncertain partial delivery is never automatically
  replayed.
- Own a Windows Job Object before resuming a new process, so cancellation and
  timeout include descendants. Unix uses an owned process group. Task write leases
  and baseline reconciliation follow actual completion, not the first RPC return.
- Keep the completed process clock fixed. Report server dispatch duration and
  observation age separately. Preserve cancellation evidence for the bounded
  retention window instead of discarding it immediately.
- Use bounded ring buffers and absolute byte cursors for output. A reader behind
  the retained tail receives an explicit output-gap indication. Exact acknowledged
  project-instruction revisions avoid retransmitting unchanged instruction text.
- Accept explicit persisted `baseline_roots` and stream selected files in 256 KiB
  chunks. The scoped path has bounded 8 GiB/file, 64 GiB aggregate and 100,000-entry
  budgets. Cancellation, traversal errors and incomplete scans are failures, not
  successful partial baselines. The original bounded whole-workspace mode remains.
- Preview supported Codex TOML and Claude Code JSON settings in the desktop
  Integrations page without activating permissions, hooks or provider models.

## Operating boundaries

Keep the desktop/server process running for long commands. Chat transport timeouts
do not imply command failure, but this version does **not** implement a durable
restart-surviving job supervisor or automatic command replay. `survives_server_restart`
is explicitly false. Stop or checkpoint work before updating or restarting the app.

There is no claim of a completed seven-day wall-clock endurance test. Accelerated
clock tests exercise 90-minute cache expiry and fourteen-day time values; real
process tests exercise ordinary no-deadline execution, polling and cancellation.
RAM-only describes this application's disposable output/receipt caches, not a ban
on OS paging or on a child program's own logs, checkpoints, compiler artifacts or
downloaded executables. Those are not silently moved or deleted. Complete logs
and durable checkpoints still need an explicitly approved output directory.

Configuration preview is not drop-in activation of all provider policies and is not
proof of Codex-equivalent OS sandboxing. Full provider orchestration and the separate
workspace-history consolidation redesign are not claimed by this release.

## Verification and release policy

The regression cases exercise real local processes: zero-wait input, frozen terminal
time, output rollover, retained cancellation evidence, linked-project task identity,
simultaneously running independent projects and descendant cancellation. Scanner and
configuration checks use synthetic local fixtures, not actual YOLO training or model
requests. A stable publication requires passing native compatibility checks, strict lint/format,
frontend checks/build and verification of the exact packaged artifact. The release
asset list identifies the platforms actually built; no unbuilt platform is implied.

See [long-running commands](../long-running-commands.md) for the polling contract and
the distinction between tool response time, process duration and total chat time.

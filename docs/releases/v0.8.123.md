# Coding Tools v0.8.123

## English

### Proxy

- **Every route you pick on the Proxy page is now enforced, for all of the app's traffic.** The app runs one small proxy router on this computer (127.0.0.1). Its windows and Browser tabs, update checks and downloads, App plugin and component downloads, agents with their tools and MCP servers, CPA and the Antigravity CLI all reach the network through it. For each connection it uses the route the Proxy page shows: a proxy, signed in, or Direct.
  - **Routes per model provider and per model account now apply.** Before, a provider's own proxy was saved but not used, and CPA kept the previous proxy (Decodo) after Global Routing was turned off. Each CPA credential can now have its own route too: follow its provider, Direct, or a proxy. The app applies it in CPA while CPA runs. Model traffic goes through CPA, so it follows these routes; agents and their tools follow the App route.
  - **A route change applies without restarting CPA, the agents or their tools.** The router uses the new route for the next connection.
  - **Nothing falls back to Direct by itself.** A route whose proxy was removed or turned off, refuses the sign-in or can't be reached fails with an error that names the reason. It does not quietly go direct or through another proxy.
  - **The proxy's password stays in the app.** Programs the app starts get only the router's local address and a key, so an agent's tool can no longer print the proxy's sign-in from its environment. Programs the app didn't start can't use the router without that key. The one exception is a port opened only for ChatGPT Desktop while it runs, because it can't send a sign-in; that port carries the App route.
  - **SOCKS5 proxies with a sign-in, and SOCKS4 proxies, work for every route.** Browser windows could not sign in to a SOCKS proxy before, and 0.8.122's relay handled only HTTP(S) proxies.
  - App plugins, updates and component downloads use the App route. They no longer use the route of whichever Browser-tab account is on screen.
  - Removing a proxy that routes still use asks where those routes go instead: another proxy, or Direct. Before, they turned off silently.
  - This replaces 0.8.122's sign-in relay.
- **The Proxy page shows where traffic goes.**
  - A line at the top says whether all app traffic goes through a proxy, goes direct, or is blocked because the chosen proxy is gone. A banner appears when the router is down (routed traffic is blocked, never sent direct) or had to move to another port.
  - Each proxy shows its last test inline: sign-in accepted or refused, speed, **exit IP and country**, and when it ran. A failed test shows its error on the card, not only on hover. The card also says how many routes use the proxy.
  - **Routes** lists the App, All model providers, each provider by name (Codex, Claude, Gemini, Antigravity, Provider Manager and the others CPA lists), every model account (with a search), and the Browser-tab accounts. Each row shows where it really goes now, with live counters: open connections, last use and the last failure. Picking a proxy on a row that had none now works.
  - **What follows these routes** shows the router, the app itself, agents and their tools, CPA, ChatGPT Desktop, and your own Chrome, which is not routed.
- **Restart once after updating.** Agents and CPA that were already running keep their old route until they restart. The page offers "Apply" for CPA.

### Approvals

- **"Let the model judge" works when the chat's model refuses a setting (#1309).** With the Codex accounts out of quota, CPA served the chat's model from an OpenAI API key that refuses `max_tokens` and `temperature: 0`. The judge got HTTP 400, and every request was denied without a judgement ("Unsupported parameter: 'max_tokens'…").
  - The app now asks again without a setting the model says it refuses, and remembers that for the model.
  - This covers all of the app's own model calls: the reviewer and judge, chat titles, goal checks, grading and summaries.
  - **Cost:** the judge's answer then comes from that API key, which bills it. Before, those calls failed and cost nothing.

### Chat (Agent Orchestrator)

Agent Orchestrator is pinned at 50b709c03 (AO#45, AO#44 and AO#43).

- **Pressing Stop twice no longer leaves your messages stuck (AO#45).** While an agent was winding a turn down, a second Stop was refused, and that refusal made the chat forget the first Stop. Messages queued before Stop were then neither cancelled nor sent, and anything typed after it sat queued with nothing running. Stop now keeps its effect however many times it is pressed.
- **A Codex chat no longer hangs as "working" when the database is busy (AO#45).** If the database was busy at the moment a Codex turn finished, the chat lost that event after a single try: the turn stayed "working" and every later message queued behind it. The chat now waits for the database, as Claude Code chats already did.
- **Messages go out in the order you typed them after a failed turn (AO#45).** When a turn failed, a message already waiting stayed queued, and the next one you sent ran ahead of it. The waiting message now goes first.
- **A Claude Code chat whose Claude process died continues on your next message (AO#44).** Claude Code's adapter drops a chat's session when the Claude process behind it dies, but AO kept the old session and still showed the chat as ready.
  - The next message failed with `set ACP session option "model"`: Resource not found, and the chat moved to a fresh agent that only got a summary. Seen on 2026-11-12 and 2026-11-13.
  - AO now reopens the same conversation on the running adapter and sends the message. Claude Code restores it from its own transcript, so the chat keeps what it knew.
  - Until it is reopened, the chat shows as recovering instead of ready. If it can't be reopened, the message fails with "the stored provider conversation could not be resumed" instead of an internal error, and the next message tries again.
- **A message sent right after a turn ends no longer waits behind a read of the whole chat (AO#43).** When a turn finishes, AO looks for the chat's next queued message while it holds the lock that a new send needs.
  - That check read every message the chat had ever had; in 0.8.113 it read every chat's messages. On 2026-11-13 a follow-up waited 6 minutes, and the chat moved to a fresh agent that only got a summary.
  - It now reads only the queue. In a test database with a 12,000-message chat, that is 1 page instead of 9,226 when nothing is queued, and 13 pages instead of 9,235 with one queued message.
  - AO adds a small index of queued turns (migration 9008). It is built once, on the first start after the update, by reading the turns table.

## 繁體中文

### 代理

- **你在「代理」頁面選擇的每條路由，現在都會套用到 App 的所有流量。** App 會在本機（127.0.0.1）執行一個小型代理路由器。App 的視窗與瀏覽器分頁、更新檢查與下載、App 外掛與元件下載、Agent 及其工具與 MCP 伺服器、CPA 以及 Antigravity CLI，全部都經由它連上網路。每條連線都會依照「代理」頁面顯示的路由送出：經由代理伺服器（已登入），或直接連線。
  - **各模型供應商與各模型帳號的路由現在會生效。** 以前供應商自己的代理雖然有儲存，但不會被使用；關閉「全域路由」後，CPA 仍沿用之前的代理（Decodo）。現在每個 CPA 憑證也可以有自己的路由：跟隨其供應商、直接連線，或指定代理。App 會在 CPA 執行期間直接套用。模型流量經由 CPA，因此會遵循這些路由；Agent 及其工具則遵循 App 路由。
  - **變更路由不需重新啟動 CPA、Agent 或其工具。** 路由器會在下一條連線使用新路由。
  - **不會自行改為直接連線。** 若路由所用的代理已移除或停用、拒絕登入或無法連線，該連線會失敗並說明原因，不會悄悄改為直接連線或經由其他代理。
  - **代理密碼只留在 App 內。** App 啟動的程式只會取得路由器的本機位址與一組金鑰，因此 Agent 的工具無法再從環境變數中印出代理的登入資訊。不是由 App 啟動的程式，沒有金鑰就無法使用路由器。唯一的例外是 ChatGPT Desktop 執行期間專為它開啟的連接埠，因為它無法傳送登入資訊；該連接埠走 App 路由。
  - **需要登入的 SOCKS5 代理與 SOCKS4 代理，現在每條路由都能使用。** 以前瀏覽器視窗無法登入 SOCKS 代理，而 0.8.122 的中繼只支援 HTTP(S) 代理。
  - App 外掛、更新與元件下載改用 App 路由，不再使用畫面上目前顯示的瀏覽器分頁帳號的路由。
  - 移除仍有路由使用中的代理時，會先詢問這些路由要改用什麼：其他代理或直接連線。以前這些路由會被悄悄關閉。
  - 此功能取代 0.8.122 的登入中繼。
- **「代理」頁面會顯示流量實際的去向。**
  - 頁面頂端會說明 App 的所有流量是經由代理、直接連線，還是因所選代理已不存在而被封鎖。路由器停止運作（經路由的流量會被封鎖，絕不會改為直接連線）或必須改用其他連接埠時，會顯示提示橫幅。
  - 每個代理會直接顯示最近一次測試結果：登入被接受或被拒、速度、**出口 IP 與國家**，以及測試時間。測試失敗時，錯誤會直接顯示在卡片上，不必停在上面才看得到。卡片也會顯示有多少條路由使用此代理。
  - **路由**列出 App、所有模型供應商、各個供應商（Codex、Claude、Gemini、Antigravity、Provider Manager 以及 CPA 列出的其他供應商）、每個模型帳號（可搜尋），以及瀏覽器分頁帳號。每一列都會顯示目前實際的去向與即時計數：開啟中的連線、最近使用時間與最近一次失敗。在原本沒有代理的列上選擇代理，現在也能正常運作。
  - **跟隨這些路由的程式**會列出路由器、App 本身、Agent 及其工具、CPA、ChatGPT Desktop，以及你自己的 Chrome（不經路由）。
- **更新後請重新啟動一次。** 已在執行中的 Agent 與 CPA 會沿用舊路由，直到重新啟動。頁面上會為 CPA 提供「Apply」。

### 審批

- **聊天模型拒絕某個參數時，「讓模型判斷」仍能運作（#1309）。** Codex 帳號額度用完時，CPA 改由 OpenAI API 金鑰提供聊天模型，而該模型不接受 `max_tokens` 與 `temperature: 0`。判斷因此收到 HTTP 400，所有請求都未經判斷就被拒絕（「Unsupported parameter: 'max_tokens'…」）。
  - 現在 App 會在模型表示不接受某個參數時，去掉該參數重新詢問，並記住此模型的限制。
  - 適用於 App 自己的所有模型呼叫：審查與判斷、對話標題、目標檢查、評分與摘要。
  - **費用：** 此時判斷的回答來自該 API 金鑰，會由該金鑰計費；以前這些呼叫會失敗，不產生費用。

### 對話（Agent Orchestrator）

Agent Orchestrator 固定於 50b709c03（AO#45、AO#44 與 AO#43）。

- **連按兩次「停止」不再讓訊息卡住（AO#45）。** Agent 正在結束回合時，第二次「停止」會被拒絕，而這次拒絕讓對話忘了第一次「停止」。結果在「停止」之前排入佇列的訊息既沒有被取消，也沒有送出；之後輸入的訊息也一直排在佇列中，沒有任何工作在執行。現在不論按幾次，「停止」都會維持效果。
- **資料庫忙碌時，Codex 對話不再一直顯示「工作中」（AO#45）。** 以前如果 Codex 回合結束的那一刻資料庫正忙，對話只試一次就丟掉該事件：回合一直顯示「工作中」，之後的每則訊息都排在它後面。現在對話會等待資料庫，與 Claude Code 對話原本的做法相同。
- **回合失敗後，訊息會依你輸入的順序送出（AO#45）。** 以前回合失敗時，已在等待的訊息會留在佇列中，而你接著送出的下一則訊息會搶先執行。現在等待中的訊息會先送出。
- **Claude Code 對話背後的 Claude 程序意外結束後，下一則訊息會接續原本的對話（AO#44）。** Claude 程序結束時，Claude Code 的轉接器會丟棄該對話的工作階段，但 AO 仍保留舊的工作階段，並繼續把對話顯示為「就緒」。
  - 下一則訊息因此以 `set ACP session option "model"`：Resource not found 失敗，對話被移交給只拿到摘要的新 Agent。2026-11-12 與 2026-11-13 各發生一次。
  - 現在 AO 會在仍在執行的轉接器上重新開啟同一段對話，再送出訊息。Claude Code 會從自己的對話紀錄還原，所以對話保有先前知道的一切。
  - 重新開啟之前，對話會顯示為「復原中」而非「就緒」。如果無法重新開啟，訊息會以「無法恢復已儲存的對話」失敗，不再是內部錯誤，下一則訊息會再試一次。
- **回合結束後立刻送出的訊息，不再卡在整段對話的讀取後面（AO#43）。** 每個回合結束時，AO 會一邊持有「送出新訊息」所需的鎖，一邊查找這段對話的下一則排隊訊息。
  - 這項檢查過去會讀取該對話的全部訊息；0.8.113 甚至會讀取所有對話的訊息。2026-11-13 一則後續訊息因此等了 6 分鐘，對話被移交給只拿到摘要的新 Agent。
  - 現在只讀取佇列。在含 12,000 則訊息的測試對話中，沒有排隊訊息時只讀 1 頁（原本 9,226 頁）；有一則排隊訊息時讀 13 頁（原本 9,235 頁）。
  - AO 新增一個只收錄排隊回合的小型索引（migration 9008）。更新後第一次啟動時，會讀取回合資料表一次來建立它。

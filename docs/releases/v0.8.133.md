# Coding Tools v0.8.133

## English

### Chats: a turn Claude starts by itself

- **A turn Claude starts by itself now shows in the chat, and its permission requests can be answered.** Claude Code can start working without a message from the chat, for example when another Claude session on this computer sends it a message. Before, such a turn ran unseen: the chat read Done while its first permission request waited, sometimes for hours. The chat now shows the turn with "Claude continued on its own." as its message, its requests appear as usual and "Approve for me" reviews them, and its answer is shown when it finishes. The app checks for such turns every two minutes, also while the window is minimized.
- **Agent Orchestrator tracks such a turn.** AO now asks Claude's agent to report these turns, records each as a turn of its own with its permission requests, and Stop interrupts it. A turn that was running when AO restarted is kept if it still runs, and is settled if it ended in the meantime.

### Chat pages: close a page

- **A chat page can be closed.** Right-click a page's number at the foot of the chat and choose **Close page**, middle-click the number, or press Delete on it, as you would close a browser tab. Before, pages only accumulated. The last page stays open.
- **Closing a page only takes its chats off screen.** Their runs and queued messages carry on, and the chats stay in the chat list. If the closed page was open, the page before it opens.
- **The other pages keep their chats.** The pages after a closed one move up a place with their chats, split layout and unsent new-chat text as they were. A new page never picks up anything of a closed one. The layout is kept across restarts.

### Computer use: windows with many controls

- **An agent can see a window with many controls.** For each snapshot, Codex's computer-use engine reads the window's accessibility text along with the screenshot. It gives up on the text after 8 seconds and then fails the whole read. A window with roughly a thousand controls or more takes that long every time, and on a busy computer fewer do. Such a window could not be seen at all: every snapshot failed with "The Codex engine refused this call (CODEX_CAPTURE_FAILED)". The snapshot now reads the window again for its screenshot alone, as the engine advises, and tells the agent the text was unavailable. For a minute after that, snapshots of that window skip the text and arrive in under a second.

### MCP: a revoked ChatGPT sign-in says so

- **An account whose sign-in ChatGPT revoked now says "Sign in to it again" instead of "MCP ownership metadata is unavailable or exceeded its bound."**
  - On 2026-11-17, Connect failed on several accounts even though the MCP tunnel was ready. The automatic setup also failed, and retried every few minutes.
  - The accounts' sign-in pages still reported them as signed in, but ChatGPT answered every request with HTTP 401 ("token_revoked").
  - Because ChatGPT labels that answer as plain text, the app read it as missing metadata.
  - The card now reads "ChatGPT no longer accepts this account's sign-in. Sign in to it again in the Browser tab, then retry." Automatic setup waits for you to sign in instead of retrying.

### Browser: sign in to OpenAI Platform

- **An account can now sign in to OpenAI Platform in the Browser tab.**
  - Connect MCP stopped at Platform's sign-in for several accounts ("OpenAI Platform asked this account to sign in again"), and there was nowhere to finish it.
  - In the Browser tab, Platform's Continue buttons were treated as a ChatGPT sign-in and handed to Chrome, which only showed ChatGPT again. They now stay in the tab.
  - A card that stopped at Platform's sign-in has a **Sign in to OpenAI Platform** button. It switches to that account and opens Platform's sign-in in the Browser tab.
  - **Platform settings** under More tunnels opens in the Browser tab on the tunnel's account. Before, it opened an invisible window and held the browser for up to 15 minutes.

### Agent Orchestrator: a slow first start is waited for

- **A slow first start after an update is waited for instead of being stopped at 15 minutes.**
  - On 2026-11-16, the first start after the 0.8.124 update rebuilt an index over a 4.7 GB database. Agent Orchestrator printed nothing for 15 minutes, so the app stopped it as hung and started it again.
  - That throws the work away: the rebuild runs in one transaction. On a slower disk or a larger database, every start would have been stopped the same way.
  - Agent Orchestrator now reports what it is doing while it starts: each stage, the database update it is running, and how much reading, writing and CPU work it has done. It reports every 15 seconds.
  - Past 15 minutes, the app keeps waiting while those reports show work. It still stops a start that has shown no work for 5 minutes, or that is still working after 3 hours.
  - The app log's slow-start entries now name the stage and the database update, for example "migrate 9009_conversation_activity_page_keys_index.sql".

### CPA: Provider Manager 0.9.0

- **An API key with no credits stops getting requests.** When a key answers that it has no credits, Provider Manager now leaves it out of smart routing and tells CPA's own selector to skip it too. This covers OpenAI's "You have no credits remaining", Anthropic's "credit balance is too low", DeepSeek's "Insufficient Balance" and HTTP 402. Before, every request kept going to it and failed after about a minute. The key is retried after 30 minutes, then 1, 2, 4, 8 and at most 12 hours. A request that succeeds on it, or **Credits added** in Provider Manager > Accounts > Fallbacks, puts it back at once.
- **API keys are fallbacks you choose.** For a model your sign-in accounts serve, an API key or another provider is used only if you turn it on under **Provider Manager > Accounts > Fallbacks**, and only after every sign-in account is spent. Without that, the request is refused with a reason that says how many keys could serve it. Models that only keys serve work as before.
- **Your API keys are no longer stored in Provider Manager's usage log.** A configured key used to be saved as each request's source. It is now kept as its last four characters, and older lines are hidden the same way when read.

## 繁體中文

### 對話：Claude 自行開始的回合

- **Claude 自行開始的回合現在會顯示在對話中，其權限請求也能回覆。** Claude Code 可能在對話沒有傳送訊息時自行開始工作，例如本機另一個 Claude 工作階段傳訊息給它。以往這類回合在背景執行、無人看見：對話顯示「完成」，而它的第一個權限請求卻一直等待，有時長達數小時。現在對話會顯示這個回合，訊息為「Claude continued on its own.」；它的請求照常出現，「Approve for me」也會審查，完成後會顯示它的回答。App 每兩分鐘檢查一次這類回合，視窗最小化時也會檢查。
- **Agent Orchestrator 會追蹤這類回合。** AO 現在會要求 Claude 的代理回報這類回合，將每一個記錄為獨立的回合並附上其權限請求，按「停止」即可中斷它。AO 重新啟動時仍在執行的回合會保留；期間已結束的回合則會結算。

### 對話分頁：關閉分頁

- **現在可以關閉對話分頁。** 在對話底部的分頁編號上按右鍵並選擇 **Close page**，或以滑鼠中鍵點擊編號，或在編號上按 Delete，就像關閉瀏覽器分頁一樣。以往分頁只會越來越多。最後一個分頁會保留開啟。
- **關閉分頁只會讓其中的對話離開畫面。** 它們的執行與排隊中的訊息會繼續進行，對話也仍留在對話清單中。若關閉的是目前開啟的分頁，會改為開啟它前一個分頁。
- **其他分頁會保留各自的對話。** 被關閉分頁之後的分頁會往前移一位，其對話、分割版面與尚未送出的新對話文字都維持原樣。新增的分頁不會帶入已關閉分頁的任何內容。版面配置在重新啟動後仍會保留。

### 電腦操作：控制項很多的視窗

- **代理現在能看見控制項很多的視窗。** Codex 的電腦操作引擎每次擷取快照時，除了螢幕截圖也會讀取視窗的協助工具文字。文字讀取超過 8 秒就會放棄，並讓整次讀取失敗。控制項約一千個以上的視窗每次都會超過這個時間，電腦忙碌時控制項較少的視窗也可能如此。這類視窗以往完全無法看見：每次快照都失敗並顯示「The Codex engine refused this call (CODEX_CAPTURE_FAILED)」。現在快照會依引擎的建議，重新只讀取該視窗的螢幕截圖，並告知代理文字無法取得。之後一分鐘內，該視窗的快照會略過文字，在一秒內完成。

### MCP：ChatGPT 撤銷登入時會明確告知

- **ChatGPT 撤銷某帳號的登入後，現在會顯示「請重新登入」，不再顯示「MCP ownership metadata is unavailable or exceeded its bound.」。**
  - 2026-11-17，即使 MCP 通道已就緒，多個帳號的「Connect MCP」仍然失敗；自動設定也失敗，並每隔幾分鐘重試一次。
  - 這些帳號的登入頁面仍顯示為已登入，但 ChatGPT 對每個請求都回覆 HTTP 401（「token_revoked」）。
  - 由於 ChatGPT 將這個回覆標示為純文字，App 誤以為是缺少中繼資料。
  - 現在卡片會顯示「ChatGPT no longer accepts this account's sign-in. Sign in to it again in the Browser tab, then retry.」，自動設定會等你重新登入，不再重試。

### Browser：登入 OpenAI Platform

- **現在可以在 Browser 分頁中為帳號登入 OpenAI Platform。**
  - 多個帳號的「Connect MCP」停在 Platform 的登入步驟（「OpenAI Platform asked this account to sign in again」），而且沒有地方可以完成登入。
  - 在 Browser 分頁中，Platform 的「Continue」按鈕被當成 ChatGPT 登入交給 Chrome 處理，結果只會再次顯示 ChatGPT。現在它們會留在分頁中。
  - 停在 Platform 登入步驟的帳號卡片會顯示「Sign in to OpenAI Platform」按鈕：切換到該帳號，並在 Browser 分頁中開啟 Platform 的登入頁面。
  - 「More tunnels」中的「Platform settings」現在會在 Browser 分頁中，以該通道的帳號開啟。之前它會開啟一個看不見的視窗，並佔用瀏覽器最多 15 分鐘。

### Agent Orchestrator：較慢的首次啟動會被等待完成

- **更新後第一次啟動較慢時，App 現在會等它完成，不會在 15 分鐘時停止它。**
  - 2026-11-16 更新到 0.8.124 後第一次啟動時，Agent Orchestrator 要在 4.7 GB 的資料庫上重建一個索引。它 15 分鐘都沒有任何輸出，App 便把它當成卡住而停止並重新啟動。
  - 這會丟掉已完成的工作：重建是在單一交易中進行。若磁碟更慢或資料庫更大，之後每次啟動都會被同樣停止。
  - Agent Orchestrator 現在會在啟動期間每 15 秒回報進度：目前的階段、正在執行的資料庫更新，以及到目前為止的讀寫量與 CPU 工作量。
  - 超過 15 分鐘後，只要回報顯示仍在工作，App 就會繼續等待；若 5 分鐘內沒有任何工作，或工作超過 3 小時仍未完成，仍會停止這次啟動。
  - App 記錄中的「啟動緩慢」項目現在會標明階段與資料庫更新，例如「migrate 9009_conversation_activity_page_keys_index.sql」。

### CPA：Provider Manager 0.9.0

- **沒有額度的 API 金鑰不再收到請求。** 當某個金鑰回應它已沒有額度時，Provider Manager 現在會把它移出智慧路由，並讓 CPA 本身的選擇器一併略過它。涵蓋 OpenAI 的「You have no credits remaining」、Anthropic 的「credit balance is too low」、DeepSeek 的「Insufficient Balance」及 HTTP 402。以前每個請求都會繼續送到它，約一分鐘後才失敗。該金鑰會在 30 分鐘後重試，之後為 1、2、4、8 小時，最長 12 小時。只要有請求在它上面成功，或在 Provider Manager > Accounts > Fallbacks 按下 **Credits added**，就會立即恢復使用。
- **API 金鑰是由您選擇的備援。** 對於您的登入帳號可提供的模型，只有在 **Provider Manager > Accounts > Fallbacks** 中開啟的 API 金鑰或其他供應商才會被使用，而且只在所有登入帳號都已用完之後。未開啟時，請求會被拒絕，並說明有多少個金鑰可以提供該模型。只有金鑰能提供的模型則照舊運作。
- **您的 API 金鑰不再儲存在 Provider Manager 的使用紀錄中。** 以前設定的金鑰會被存成每個請求的來源，現在只保留最後四個字元；較舊的紀錄在讀取時也會同樣隱藏。

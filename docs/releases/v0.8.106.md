# Coding Tools 0.8.106

## English

### Error messages: top-left, past the sidebar, and gone after 5 seconds (#1150)
- **The "Something went wrong" box moves from the bottom-right to the top-left of the page,** a small gap past the sidebar and just below the title bar.
  - It follows the sidebar: past its full width when it is open, past the icon rail when it is hidden, and at the window's edge in the narrow layout. It glides along when the sidebar opens or closes.
- **It now fades out by itself after 5 seconds.** Until now it stayed up until you clicked Dismiss or did something else.
  - Pointing at it keeps it up. Moving away gives it another 5 seconds.
  - A new error replaces it and starts the 5 seconds again.

### Chats: coming back to an idle chat no longer takes 1–2 minutes (#1148)
- **A chat's agent is stopped after 30 minutes idle and brought back when you send the next message.**
  - Bringing it back used to re-import the chat's whole history one database write at a time. On a busy disk, a long chat took one to three minutes, and often ended with a new agent and a summary instead of the chat's own agent.
  - The history now goes in batches. In a timing run on the same disk this was five times faster: 3,002 events in 27 s instead of 2 min 18 s.
  - The app also starts bringing the agent back while it is still preparing the message, not after.

### Activity log: a slow agent start names its cause (#1147)
- **When an agent is slow to take a message, the app's log now says why:**
  - AO's report of who holds its database writer (`ao.writer_held`);
  - any stage of an agent's start that took 5 s or more (`ao.start_stage_slow`).
- Both stay in memory only.

### Chats: a wave of retries no longer fails all together (#1158)
- **When the agent service restarted under several running chats, "Retry automatically" relaunched every chat in the same second,** each as a new agent.
  - On a busy machine none of them started within four minutes. The launch watchdog then ended them all at once, and the next retry did the same.
  - So one restart cost each chat three or four failed attempts.
- **New agents now start at most two at a time.** The others show "waiting for N other agents to finish starting" and begin as soon as one is up or fails, or three minutes pass.
- The four-minute watchdog counts from an agent's actual start, not from its wait.

### Browser: switching the ChatGPT account no longer waits for ChatGPT to load (#1153)
- **A switch used to end only after the account's page had loaded through its proxy and passed its sign-in check.** On a busy machine that took up to a minute. All that time the account picker stayed locked on "Switching account…" and still showed the account you left.
- **Now the switch ends as soon as the account's page is on screen,** and ChatGPT goes on loading there. The picker shows the account you picked at once.
- The automatic MCP connector setup no longer refuses a switch while it runs. It stops, tries again later, and shows no error.

### Chats: Clawd's house is back under the chat list, and Clawd walks out of it (#1154)
- **On a second chat page in split view, the house stood on a pane's chat box and covered its last messages.** The pet looked for its yard on the first page, which stays loaded while hidden.
  - It now finds the yard on its own page, above Settings.
  - With the chat list hidden, there's no house in split view, and Clawd naps on its box.
- **Clawd no longer jumps from bed onto the chat box in one frame** when a turn starts or another pane calls it. It climbs out of bed, goes down the ladder, walks out onto a porch in front of the house, and leaps across in an arc.
- Leaps between panes now arc instead of sliding flat. When the house is beside the box, Clawd steps up onto its side instead of appearing there.

### Fewer whole-app freezes (#1145)
- **Five places where the app's main process froze every window, all found in the live Activity log, now run off it:**
  - The update check's fallback download: a hung GitHub connection held every window for 72.9 s when its timeout closed the socket.
  - Starting a chat's sandbox (1.4 s).
  - Reading Antigravity's folder (0.6 s).
  - The component update check (0.4 s).
  - The Windows disk-health check (0.3 s).
- **Startup after an update no longer holds the main thread on:**
  - saving settings (up to 15.5 s);
  - starting the headless service (up to 9.9 s);
  - flushing the supervisor's ownership marker (up to 2.5 s);
  - starting the bridge daemon (1.1 s).
- Settings now save in the background. Quitting waits for the save, at most 5 s.
- Identical read-only app requests that are already in flight now share one answer.
- A long mission's chat no longer keeps finished Think rows shimmering. They had the renderer using more than a full core.

### MCP: Connect no longer fails on "The browser navigation changed during MCP context inspection" (#1149)
- **OpenAI Platform's own sign-in during the tunnel check is now part of that step,** so Connect MCP goes on instead of failing.
- **A setup page that moves elsewhere now says where it went.**

### Approvals: with "Let the model judge" on, cards close on their own again (#1151)
- **An answer cut off on its way to the agent is sent again.** The reviewer's allow or deny could be cut off by its 45-second limit while it was being sent. The request then sat on its card as "delivery outcome is unknown", with Allow/Deny waiting for you even though the judge was on. Now, if the request is still waiting a minute later, the same answer goes again, up to 3 times. It is never judged a second time.
- **Meanwhile the card shows the request as being reviewed.** It comes back to you only if 3 sends never reach the agent. With the judge off, nothing changes: an uncertain answer still waits for you.

### Computer use: a Runtime > Computer use tab, and allowed apps without a review for each step (#1152)
- **A new Runtime > Computer use tab in the sidebar shows:**
  - the switch that gives chats computer use, and a new "Review each step" switch;
  - what is under control now (app, window, agent and model, current step), with a Stop button;
  - requests waiting to use an app, which you can answer there as well as in the chat;
  - always-allowed apps, with Remove and "Allow an app from your open windows", so you can allow an app before a chat asks;
  - the history of steps the agent took.
- **Once you allow an app for a chat, the agent works in that app's window without a review or prompt for each step, as in Codex.**
  - Turn on "Review each step" to have every step reviewed again.
  - Blocked commands, whole-screen captures and other chats' steps are still reviewed.
- **An app you always allowed now also works in a project whose screen capture was off:** selecting its window turns screen capture on for that project. Before, every step there failed.

## 繁體中文

### 錯誤訊息：移到左上角、側邊欄旁，5 秒後自動消失（#1150）
- **「Something went wrong」訊息框由右下角移到頁面左上角，**與側邊欄保持一小段間距，位於標題列下方。
  - 它會跟隨側邊欄：側邊欄展開時排在完整寬度之後，收起時排在圖示欄之後，窄版面時則貼近視窗邊緣。側邊欄開合時它會一同滑動。
- **現在會在 5 秒後自動淡出。** 之前它會一直顯示，直到你按下 Dismiss 或進行其他操作。
  - 滑鼠指向它時會保持顯示；移開後再顯示 5 秒。
  - 出現新的錯誤時會取代它，並重新計算 5 秒。

### 對話：回到閒置的對話不再需要等 1 至 2 分鐘（#1148）
- **對話的代理閒置 30 分鐘後會停止，傳送下一則訊息時再重新啟動。**
  - 以往重新啟動時，系統會把整段對話紀錄逐筆寫回資料庫。在忙碌的磁碟上，較長的對話要花一到三分鐘，最後還常常改由新代理接手並附上摘要，而不是原本的代理。
  - 現在對話紀錄改為分批寫入。在同一顆磁碟上的計時測試快了五倍：3,002 筆事件由 2 分 18 秒縮短為 27 秒。
  - 應用程式在準備訊息的同時就開始喚回代理，不必等準備完成。

### 活動記錄：代理啟動緩慢時會指出原因（#1147）
- **代理遲遲未接收訊息時，應用程式記錄現在會指出原因：**
  - AO 回報目前由誰占用其資料庫寫入權（`ao.writer_held`）；
  - 代理啟動時任何耗時 5 秒以上的階段（`ao.start_stage_slow`）。
- 兩者都只保留在記憶體中。

### 對話：大量重試不再一起失敗（#1158）
- **代理服務在多個對話執行中重新啟動時，「自動重試」會在同一秒內讓每個對話各自啟動一個新代理。**
  - 在忙碌的電腦上，這些代理都無法在四分鐘內啟動完成，啟動監視器便同時把它們全部結束，下一次重試又重演一次。
  - 因此一次重新啟動會讓每個對話失敗三到四次。
- **現在新代理最多同時啟動兩個。** 其他的會顯示「等待其他 N 個代理完成啟動」，並在其中一個啟動完成或失敗，或經過三分鐘後立即開始。
- 四分鐘的啟動監視從代理實際開始啟動時計算，不包含等待時間。

### 瀏覽器：切換 ChatGPT 帳戶不再需要等 ChatGPT 載入完成（#1153）
- **以前要等該帳戶的頁面經由其代理載入完成、並通過登入檢查後，切換才算結束。** 在忙碌的電腦上最久要一分鐘，期間帳戶選單一直停在「正在切換帳戶…」，而且仍顯示原本的帳戶。
- **現在只要該帳戶的頁面出現在畫面上，切換就完成，** ChatGPT 接著在頁面中繼續載入；帳戶選單會立即顯示您選的帳戶。
- 自動建立 MCP 連接器的作業執行時也不再阻擋切換：它會停下、稍後再試，且不會顯示錯誤。

### 對話：Clawd 的小屋回到聊天清單下方，Clawd 也改為走出小屋（#1154）
- **在分割畫面的第二個聊天分頁上，小屋會站在窗格的輸入框上，擋住最後幾則訊息。** 寵物去第一個分頁找它的院子，而第一個分頁隱藏時仍保持載入。
  - 現在它會在自己所在的分頁找到院子，就在「設定」上方。
  - 聊天清單隱藏時，分割畫面不再顯示小屋，Clawd 會在輸入框上打盹。
- **開始新一輪對話或其他窗格呼叫時，Clawd 不再一格畫面就從床上跳到輸入框。** 它會下床、爬下梯子、走到小屋前的門廊，再以弧線跳過去。
- 窗格之間的跳躍現在會有弧線，不再像平移滑過；小屋在輸入框旁邊時，Clawd 會一步跨上輸入框側邊，而不是直接出現在那裡。

### 減少整個程式凍結（#1145）
- **以下五處曾讓程式主行程凍結所有視窗（皆見於實際的活動記錄），現在都改在主行程之外執行：**
  - 更新檢查的備援下載：一次卡住的 GitHub 連線在逾時關閉時，讓所有視窗停住 72.9 秒。
  - 啟動對話的沙箱（1.4 秒）。
  - 讀取 Antigravity 的資料夾（0.6 秒）。
  - 元件更新檢查（0.4 秒）。
  - Windows 磁碟健康檢查（0.3 秒）。
- **更新後啟動時，以下工作不再佔住主執行緒：**
  - 儲存設定（最長 15.5 秒）；
  - 啟動無介面服務（最長 9.9 秒）；
  - 寫入監管程式的擁有權標記（最長 2.5 秒）；
  - 啟動橋接背景程式（1.1 秒）。
- 設定現在在背景儲存；結束程式時會等待儲存完成，最多 5 秒。
- 正在進行中的相同唯讀請求現在共用同一個答覆。
- 長時間任務的對話不再讓已完成的「思考」列持續閃爍；它們曾讓介面佔用超過一整個 CPU 核心。

### MCP：連接不再因「The browser navigation changed during MCP context inspection」失敗（#1149）
- **通道檢查期間 OpenAI Platform 自身的登入現在屬於該步驟的一部分，**因此連接 MCP 會繼續進行，而不是失敗。
- **設定頁面若轉往他處，現在會指出它去了哪裡。**

### 審批：開啟「讓模型判斷」時，卡片會再次自動關閉（#1151）
- **送往代理途中被中斷的答覆會再送一次。**審核者的允許或拒絕可能在送出時被 45 秒上限中斷，請求便停在卡片上顯示「答覆是否送達未知」，即使已開啟「讓模型判斷」，允許／拒絕仍等著你。現在若一分鐘後請求仍在等待，會再次送出同一個答覆，最多 3 次，絕不重新判斷。
- **期間卡片會顯示該請求正在審核中。**只有 3 次都未送達代理時才會交回給你。關閉「讓模型判斷」時一切照舊：送達不確定的答覆仍由你決定。

### 電腦操作：新增「Runtime > 電腦操作」分頁，已允許的應用程式不再逐步審核（#1152）
- **側邊欄新增「Runtime > 電腦操作（Computer use）」分頁，顯示：**
  - 讓聊天使用電腦的開關，以及新的「逐步審核」開關；
  - 目前正在控制的內容（應用程式、視窗、代理與模型、目前步驟），並附「停止」按鈕；
  - 等待使用應用程式的請求，可在這裡或聊天中回覆；
  - 永遠允許的應用程式，可移除，也可「從開啟的視窗允許應用程式」，在聊天提出請求前先允許；
  - 代理已執行步驟的記錄。
- **為某個聊天允許應用程式後，代理在該應用程式視窗中的每一步不再逐一審核或詢問（與 Codex 相同）。**
  - 開啟「逐步審核」可恢復逐步審核。
  - 被封鎖的指令、整個螢幕的擷取，以及其他聊天的步驟仍會審核。
- **永遠允許的應用程式現在也能在關閉螢幕擷取的專案中使用：**選取其視窗時會為該專案開啟螢幕擷取。之前在這類專案中每一步都會失敗。

# Coding Tools 0.8.110

## English

### CPA: Cline Pass comes back by itself after its helper stops (#1177)
- **Cline Pass models no longer stay broken after the switcher's helper process stops.**
  - CPA runs Cline Pass through a small helper program. When that helper stopped (closed together with the app's processes, or crashed), CPA never started it again. Every Cline Pass model then failed with "Upstream HTTP 500" until CPA itself was restarted.
  - Now the next Cline Pass request starts the helper again with the same settings. If it keeps stopping, it is tried at most every 30 seconds.
- Cline Pass switcher plugin 0.1.0-codingtools.11.

### Performance: the first start after an update no longer freezes for seconds (#1178)
- **Every app update froze Coding Tools for several seconds the first time it started** (7.9 s at 0.8.108's first start, 2026-11-10).
  - The app keeps a backup of the old, retired services' data, and takes a new one whenever its service settings change.
  - The path of the program CPA runs from includes the app's version folder, so every update changed those settings. Each update therefore took a new backup, writing a 6.5 MB index of the retired files before any window could respond.
- **Where a service runs from no longer counts as a change.** Any other change to the settings still gets its own backup, as before.

### App plugins: rebuilt plugins show how far behind upstream they really are (#1179)
- **Grok login always said an update was available.** It is built for Coding Tools from grok2api, but its own version (0.1.0) isn't grok2api's (3.1.8). Comparing the two offered the update forever, even after a rebuild from that release.
- **Plugins built into the app now compare the upstream commit they were built from** with upstream's newest release, or with its main branch when it has no release yet. The row says so, for example "Built from 7c889a9; v3.1.8 has 24 newer commits." A newer one still arrives in an app update.
- **Cline Pass switcher and CPA Helper no longer show a blank "latest".** Their repositories have no releases, and the row now says what they were built from.
- **CPA Helper is no longer offered for auto-update from GitHub**, where there is nothing to install. It is built into the app.

### Performance: an Antigravity CLI update no longer freezes the app (#1179)
- **The Antigravity CLI's automatic update to 1.5.4 froze every window** for 1.1 s and then 2.9 s (2026-11-10). Unpacking the download and writing the new version's files ran on the app's main thread.
- **All of an install or update now runs off the main thread:** the download, the archive checks, the unpacking and every file write. The checks themselves are the same, against unsafe paths and link entries.

### Chats: Clawd and its house, remade (#1180)
- **Clawd's house no longer covers the chat.** Whenever the window left no room beside the chat box, the 160 px doll's house stood on the box's top edge, over the last messages. Clawd now has a small cottage (88 × 64 px). It stands beside the box's right end, level with the box and never above its top edge. If there's no room there, it sits in the corner under the chat list. With neither, Clawd naps on its box.
  - The cottage shows what Clawd is up to: the window lights up while it's home, smoke rises from the chimney while it cooks, and z's float over the roof while it sleeps.
  - Click the cottage to look inside. The rooms open in a small panel with Clawd at half size cooking, bathing, reading or asleep in bed, and every piece of furniture is clickable. Click outside the panel or press Esc to close it.
- **Clawd moves like a little creature, not a sliding picture.**
  - When it walks, it speeds up and slows down, and its feet and a small bob follow the distance it covers, so its feet never slide. It turns round before walking back the other way.
  - A leap crouches, flies an arc and lands with a squash and a puff of dust. Let go after a drag, it falls faster and faster and lands harder the further it fell.
  - It goes into the cottage through the door, its back to you, shrinking into the doorway. It comes back out growing to full size.
  - It stands on the box's top edge (it used to hover 8 px above it), and it no longer walks down the box's sides or upside down underneath.
  - It is drawn on every refresh of a 60 Hz screen. It used to skip every other frame whenever a timer ran late, so it moved in fits at about 35 frames a second. On faster screens it stays at 60 frames a second.
  - Leaps were CSS transitions racing timers, so a busy window could land Clawd before it arrived or leave it squashed in mid-air. Now a slow frame only makes it a moment late.
- **Clawd stops only where it covers nothing to read or click** just above the box: not on the chat's last line, and not on the branch chip. When text runs right across the box, it stands where it covers least.
- The cottage panel and Clawd's speech bubble now use the chat's colours when drawn over the page. They used to show white text on white.

### Performance: hidden "scroll to bottom" dots stop animating (#1181)
- **Every working chat animated its "scroll to bottom" button's three dots, even while the button was hidden** at the bottom of the thread. During a freeze on 2026-11-10, 21 of these animations were running, 9 of them on buttons nobody could see, over a very large chat page.
- **Hidden, the dots now stand still.** They move again as soon as the button shows, and its fade is unchanged.

### Speed: automatic MCP setup stops reopening ChatGPT in hidden windows every minute (#1182)
- **The app no longer keeps loading ChatGPT in the background while chats are busy.**
  - Automatic MCP setup opens ChatGPT's plugins page in a hidden window for each signed-in account. When the app lost focus, or a chat started working before it finished, the setup stopped and started over from the beginning a minute later.
  - Seen on 2026-11-10: with busy chats this happened every 1–2 minutes and never connected anything. It started 19 hidden ChatGPT and OpenAI Platform pages in 10 minutes, almost one running at all times.
  - Now a setup that stops once is tried again on the next pass, as before. One that keeps stopping waits 2, 4, 8, 16, then 30 minutes. Clicking Connect yourself, or switching accounts, still retries at once.

### Performance: launching a chat and saving subagents no longer freeze the app (#1183)
- **Launching a chat could freeze every window for over a second.** Each launch checked whether the project folder is a git repository on the app's main thread, and on the busy hard disk that check took 1.3 s (2026-11-10).
- **Saving Runtime > Subagents froze every window for about a second.** The file was written on the main thread (0.5 s + 0.5 s).
- **Both now run off the main thread.**
  - The new subagent settings apply at once.
  - Saves are written one after another, so the file always ends with the last one.
  - If the disk refuses the write, the settings go back and the error is shown.

### Subagents: choose each model's provider, and keep subagents off providers you turn off (#1184)
- **On Runtime > Subagents, every model now starts with its provider.** Pick Antigravity, Gemini CLI, Cline Pass, Codex, Codex (own account) and so on, then one of that provider's models, then its effort. When the new provider also serves the model you had (Gemini 3.8 Flash on Antigravity or on Gemini CLI), the model and its effort stay.
- **A new Providers list switches each provider on or off**, so subagents don't use up a quota you want to keep for your own chats.
  - Subagents use only providers that are on. This includes models a chat agent picks for a subagent by itself: those providers' models are left out of what it can choose, and a start on one is refused with the reason.
  - A subagent saved on a provider you turn off shows "(off)", and the page warns that it won't start until you pick another model.
  - After you turn one off, a provider that appears later starts off. Turning every provider back on allows them all again, new ones too.
  - While some providers are off, a subagent whose model's provider can't be determined (CPA's model list unreadable) is not started, rather than risk the wrong provider.

### Fix: Pi and opencode chats no longer fail at once with "cannot honor the saved permission tuple" (#1185)
- **A chat moved to Pi or opencode now starts.**
  - Picking a model on Pi or opencode kept the permission mode picked before on Claude Code or Codex (by default "Approve for me"). Those two agents can't take a mode, so the app refused every launch: "Launch failed: This adapter cannot honor the saved permission tuple; choose a supported mode explicitly."
  - Their permission menu offers no mode to pick instead, so the chat could never start. Seen on 2026-11-10 with GPT-6.1 Sol on Pi.
  - Now a mode goes only to an agent that takes one (Claude Code, Codex, Antigravity, Native Codex). On Pi and opencode the chip shows Custom: they run on their own permissions. A chat saved with the old mode, and the model a new chat starts with, are fixed the same way, so a follow-up in a failed chat works.
- **"Retry automatically" no longer spends eight attempts on a launch the app refused.** A refused launch fails the same way within a second each time, so the card now says to change the model or permissions and send a follow-up. A launch that timed out is still retried.

### Speed: working chats stop polling the local services twice a second (#1186)
- **With many chats working, the app's background services use far less CPU.**
  - Each working chat checks its agent every half second. Each check asked the AO service for the agent's session and its latest conversation, and asked the local execution service for the chat's run. That happened even when the agent had simply been working for minutes.
  - Seen on 2026-11-10 with nine chats working: 17 run reads and 14 session reads a second. The local execution service and the AO service each used about a sixth of a CPU core, and the app's main process another sixth.
  - Now a chat whose agent is just working is checked every 1.5 seconds. A chat waiting on you (a tool approval or a question), a chat that is starting, or one with a message queued is still checked every half second. Anything you do in the app (a follow-up, a retry, Stop) is picked up as fast as before.
  - The only difference you may notice: the end of a turn, or a new tool request, can show up to one second later than before. The reply you watch streaming in is unchanged.

### Fix: quitting no longer leaves a temp file in the app's data folder (#1187)
- **Every quit left a `window-state.json.tmp-*` file behind**, and 50 had piled up by 2026-11-10.
  - When the app quits it saves the window's position, then started a second save of the same position.
  - The app exited during that second save, before it could finish and remove its temp file.
- **A quit now saves once.** The second save happens only when an earlier one is still being written, so the older position can't land last.
- **The leftover temp files are removed at the next start**, off the main thread. Only this file's temp files older than 10 minutes go.

### Chats: every harness shows its own icon (#1188)
- **The harness list shows each agent's real icon.** Many logos in the list came from another app's set and weren't the products' own:
  - Claude Code showed a pixel mascot, Qwen Code showed Alibaba Cloud's logo, Kimi showed Moonshot's striped ball, and Grok Build showed a stray "xI".
  - Gemini CLI showed the Gemini model's sparkle, Amp its old chevrons, Pi a scribble, and Muse Code a beige maze.
  - opencode, Cline, Cursor and Kilo Code were faded grey outlines.
  - Each now shows the icon its own website or repository uses: Claude Code's orange spark on a dark tile, Qwen's star, Kimi's "K", the SpaceXAI symbol for Grok Build, Gemini CLI's ">" tile, Amp's tile, Pi's pixel P, Meta's mark for Muse Code, and opencode's, Cline's, Cursor's and Kilo Code's own icons.
  - The other harnesses already had their own icons and are unchanged.
- Black icons (Cline, Grok Build) turn white in the dark theme. Kimi's black "K" keeps its light backing.

### Chats: actions on a later chat page stay on that page (#1189)
- **Opening a chat while on page 2 or later jumped back to an earlier page.** Selecting a chat in the sidebar, opening one from Structure or from another project, and the split view actions all went back to the page the chat was on before.
- **They now open on the page you are looking at.** The other panes on that page stay as they are, and a chat is never shown in two places at once.
- If a chat can't be opened there, the page says "This chat could not be opened on this page." instead of moving you somewhere else.

### Fix: a message typed right after a freeze is no longer refused as "not focused" (#1191)
- **After the app froze for a while, sending a message could fail** with "Click into the Coding Tools window and try again", although it was typed into the window. This happened twice on 2026-11-10, right after freezes of 17 to 36 seconds.
  - The app learns the window was clicked a moment after the message itself arrives when it is catching up after a freeze. It then thought the window was not in front.
- **Now a send from the shown window waits up to 2 seconds** for the window's focus to register before it is refused. A minimized or hidden window, or one that never gets focus, is still refused at once.

### Speed: the local execution service does far less disk work per request (#1192)
- **Each request the app makes to its local execution service touches the disk about a fifth as often.**
  - The service keeps its settings in one data file. Before every read of it, the service looked up and resolved the path of its own data folder again. On this PC that folder is a link from C: to G:, so the lookup took 17 file-system calls, and it happened twice per read. It also re-created that folder, which already existed, every time.
  - Seen on 2026-11-10 with nine chats working: about 2,000 file-system calls every half second, roughly 240 per request, with the service at about a sixth of a CPU core.
  - Now the folder's path is worked out once and remembered, and the folder is only created if it is missing. One read of the data file went from 57 file-system calls to 12.

### Fix: a Chrome sign-in can no longer take another card's ChatGPT login (#1193)
- **Chrome can be signed in to two ChatGPT logins at once** (ChatGPT's account switcher). The Chrome connector copies the profile's whole ChatGPT sign-in.
  - The copy could open as the *other* login, not the one Chrome was showing.
  - When that login was already another card in ChatGPT browser management, the new card took its email. Two cards then showed the same login, and the new one said "Not checked yet".
- **The import now checks which login it got before the card keeps it.**
  - The connector (1.1.0) tells the app which login Chrome's page is signed in as.
  - The app refuses the sign-in when the copied session opens as another login, or as a login another card already has. It also refuses when the login can't be confirmed.
  - A refused sign-in is wiped from that card. The message names the login and the card that has it, and says what to do: log out of the other login in Chrome's ChatGPT account menu, or use a Chrome profile signed in only to the account you want, then connect again.
  - The card's email and MCP setup wait for this check, so a refused sign-in leaves nothing behind.
- **An existing duplicate card stays until you remove it.** Use Remove on the card that shows "Not checked yet", then add the account again.
- The installed Chrome connector picks up 1.1.0 when Chrome reloads it (restart Chrome). Until then the app still refuses another card's login, but it can't compare against the login Chrome showed.

### CPA: quota accounts follow the current CPA connection (#1195)
- **The chat quota list could keep showing the old connection's accounts for up to 20 seconds** after CPA disconnected or its address or management key changed.
  - A new connection could also wait on a read that was still running for the old one.
  - A late refresh from the old connection could empty the new one's list.
- **Each quota read now belongs to one CPA connection** (its address and management key).
  - A disconnect drops what the old connection had read.
  - A read that finishes after the connection changed reports the quota as unavailable instead of showing the old accounts.
  - Reads on an unchanged connection still share requests and the short cache.

### CPA：Cline Pass 的輔助程式停止後會自動恢復（#1177）
- **切換器的輔助程式停止後，Cline Pass 模型不再一直無法使用。**
  - CPA 透過一個小型輔助程式執行 Cline Pass。這個輔助程式停止時（隨 App 的程序一起被關閉，或當掉），CPA 從不重新啟動它，於是每個 Cline Pass 模型都以「Upstream HTTP 500」失敗，直到 CPA 本身重新啟動為止。
  - 現在下一個 Cline Pass 請求會以相同設定重新啟動輔助程式；若它一再停止，最多每 30 秒重試一次。
- Cline Pass 切換器外掛 0.1.0-codingtools.11。

### 效能：更新後第一次啟動不再凍結數秒（#1178）
- **每次更新後第一次啟動，Coding Tools 都會凍結數秒**（2026-11-10，0.8.108 首次啟動時為 7.9 秒）。
  - 程式會為已停用服務的舊資料保留一份備份，服務設定變更時會再建立一份。
  - CPA 執行程式的路徑包含程式的版本資料夾，因此每次更新都會改變這些設定，每次更新也就建立一份新備份：在任何視窗能回應之前，先寫入 6.5 MB 的已停用檔案索引。
- **服務的執行位置不再算作變更。** 設定的其他變更仍會照舊各自建立備份。

### App plugins：重新建置的外掛會顯示實際落後上游多少（#1179）
- **Grok 登入一直顯示有更新。** 它是以 grok2api 為 Coding Tools 建置的，但它自己的版本（0.1.0）並不是 grok2api 的版本（3.1.8）。比較兩者會一直提供更新，即使已從該版本重新建置也一樣。
- **內建於程式的外掛，現在會以建置時所用的上游提交，比較上游最新的版本；上游還沒有版本時，則比較其主分支。** 該列會說明，例如「Built from 7c889a9; v3.1.8 has 24 newer commits.」。較新的版本仍會隨程式更新提供。
- **Cline Pass switcher 與 CPA Helper 不再顯示空白的「最新版本」。** 它們的儲存庫沒有發佈版本，該列現在會說明建置來源。
- **CPA Helper 不再提供從 GitHub 自動更新**，因為那裡沒有可安裝的內容；它內建於程式中。

### 效能：Antigravity CLI 更新不再讓程式凍結（#1179）
- **Antigravity CLI 自動更新至 1.5.4 時，所有視窗先凍結 1.1 秒，接著又凍結 2.9 秒**（2026-11-10）。解壓下載內容與寫入新版本檔案都在程式的主執行緒上進行。
- **安裝或更新的每個步驟現在都在主執行緒之外進行：** 下載、壓縮檔檢查、解壓縮與每次檔案寫入。檢查本身不變，同樣防範不安全的路徑與連結項目。

### 對話：重新製作 Clawd 與牠的房子（#1180）
- **Clawd 的房子不再遮住對話。** 以前只要視窗在訊息框旁邊沒有空間，160 px 的娃娃屋就會立在訊息框頂端，蓋住最後幾則訊息。現在 Clawd 改住一間小屋（88 × 64 px）。小屋立在訊息框右端旁邊，與訊息框對齊，絕不會高過訊息框頂端。旁邊沒有空間時，小屋放在對話清單下方的角落。兩處都放不下時，Clawd 就在訊息框上打盹。
  - 小屋會顯示 Clawd 在做什麼：牠在家時窗戶亮起，煮飯時煙囪冒煙，睡覺時屋頂上會飄出 z。
  - 點小屋可以看屋內。房間會在一個小面板中打開，半尺寸的 Clawd 在裡面煮飯、洗澡、看書，或在床上睡覺，每件家具都可以點。點面板外面或按 Esc 即可關閉。
- **Clawd 現在像一隻小動物在移動，而不是一張滑來滑去的圖。**
  - 走路時會加速與減速，腳步和輕微的上下起伏跟著走過的距離，因此腳不會打滑。往回走之前會先轉身。
  - 跳躍時先蹲下，沿弧線飛出，落地時壓扁並揚起一點灰塵。拖曳後放開，牠會越掉越快，掉得越高落地越重。
  - 進小屋時背對你從門口進去，邊走邊縮進門裡；出來時邊走邊長回原本大小。
  - 牠站在訊息框的頂端上（以前會浮在上方 8 px），也不再沿著訊息框側邊往下走，或倒著走到底下。
  - 在 60 Hz 螢幕上每次刷新都會重繪。以前只要計時器延遲就會跳過一格，動作一頓一頓的，大約每秒 35 格。在更高刷新率的螢幕上仍維持每秒 60 格。
  - 以前跳躍是 CSS 轉場在和計時器賽跑，視窗忙碌時，Clawd 可能還沒到就先落地，或在半空中保持壓扁。現在畫面變慢只會讓牠晚一點到。
- **Clawd 只會停在不遮住任何可讀或可點內容的位置**，也就是訊息框正上方：不會停在對話的最後一行或分支標籤上。當文字橫跨整個訊息框時，牠會站在遮住最少的地方。
- 小屋面板和 Clawd 的對話泡泡畫在頁面上方時，現在使用對話的配色。以前會變成白底白字。

### 效能：隱藏時「捲動到底部」的圓點不再動畫（#1181）
- **每個工作中的對話，即使「捲動到底部」按鈕在對話底部隱藏著，按鈕上的三個圓點仍持續動畫。** 2026-11-10 凍結期間，在一個非常大的對話頁面上有 21 個這樣的動畫在跑，其中 9 個所在的按鈕根本看不見。
- **隱藏時，圓點現在保持靜止。** 按鈕一出現就會再動起來，淡入淡出不變。

### 速度：自動 MCP 設定不再每分鐘在隱藏視窗重新開啟 ChatGPT（#1182）
- **對話忙碌時，App 不再一直在背景載入 ChatGPT。**
  - 自動 MCP 設定會為每個已登入的帳號，在隱藏視窗開啟 ChatGPT 的外掛頁面。若 App 在完成前失去焦點，或某個對話開始工作，設定便會中止，並在一分鐘後從頭再來。
  - 2026-11-10 實際觀察：對話忙碌時每 1–2 分鐘就發生一次，且始終沒有連上任何東西；10 分鐘內開啟了 19 個隱藏的 ChatGPT 與 OpenAI Platform 頁面，幾乎隨時都有一個在執行。
  - 現在只中止一次的設定仍會在下一輪重試，與以前相同；一再中止的設定則依序等待 2、4、8、16、30 分鐘。你自己按「連線」或切換帳號時，仍會立即重試。

### 效能：啟動對話與儲存子代理不再讓程式凍結（#1183）
- **啟動對話時，所有視窗可能凍結超過一秒。** 每次啟動都會在程式的主執行緒上檢查專案資料夾是否為 git 儲存庫；在忙碌的硬碟上，這項檢查花了 1.3 秒（2026-11-10）。
- **儲存「Runtime > Subagents」時，所有視窗凍結約一秒。** 檔案是在主執行緒上寫入的（0.5 秒 + 0.5 秒）。
- **兩者現在都在主執行緒之外進行。**
  - 新的子代理設定立即生效。
  - 儲存依序寫入，檔案最後一定是最後一次儲存的內容。
  - 若磁碟拒絕寫入，設定會還原並顯示錯誤。

### Subagents：為每個模型選擇提供者，並讓 subagent 不使用你關閉的提供者（#1184）
- **在「Runtime > Subagents」中，每個模型欄位現在都先選提供者。** 先選 Antigravity、Gemini CLI、Cline Pass、Codex、Codex（自己的帳號）等，再選該提供者的模型與推理強度。若新的提供者也提供同一個模型（例如 Antigravity 或 Gemini CLI 上的 Gemini 3.8 Flash），模型與推理強度會保留。
- **新的「提供者」清單可逐一開啟或關閉提供者**，避免 subagent 用掉你想留給自己對話的額度。
  - Subagent 只會使用已開啟的提供者，包括對話 agent 自行為 subagent 挑選的模型：已關閉提供者的模型不會出現在它可選的清單中，用這些模型啟動時會被拒絕並說明原因。
  - 已儲存在被關閉提供者上的 subagent 會顯示「(off)」，頁面也會提醒它在你改選模型前不會啟動。
  - 關閉任一提供者後，之後才出現的提供者預設為關閉；把所有提供者重新開啟後，則全部（包括新的）都再次允許。
  - 在部分提供者關閉時，若無法判斷某個 subagent 模型的提供者（CPA 的模型清單無法讀取），則不會啟動它，以免用錯提供者。

### 修正：Pi 與 opencode 對話不再一啟動就以「cannot honor the saved permission tuple」失敗（#1185）
- **改用 Pi 或 opencode 的對話現在能夠啟動。**
  - 在 Pi 或 opencode 上選擇模型時，會沿用先前在 Claude Code 或 Codex 選的權限模式（預設為「替我核准」）。這兩個代理程式無法接受權限模式，所以 App 每次都拒絕啟動：「Launch failed: This adapter cannot honor the saved permission tuple; choose a supported mode explicitly.」
  - 它們的權限選單也沒有可改選的模式，因此對話永遠無法開始。2026-11-10 在 Pi 上使用 GPT-6.1 Sol 時實際發生。
  - 現在權限模式只會送給能接受它的代理程式（Claude Code、Codex、Antigravity、原生 Codex）。在 Pi 與 opencode 上，權限按鈕顯示「自訂」：它們依自己的權限執行。以舊模式儲存的對話，以及新對話預設使用的模型，也以同樣方式修正，所以在失敗的對話中送出後續訊息即可繼續。
- **「自動重試」不再為 App 拒絕的啟動耗盡八次嘗試。** 被拒絕的啟動每次都會在一秒內以同樣方式失敗，因此卡片現在會提示你更換模型或權限並送出後續訊息。逾時的啟動仍會自動重試。

### 速度：對話工作時不再每秒兩次查詢本機服務（#1186）
- **多個對話同時工作時，App 的背景服務佔用的 CPU 大幅減少。**
  - 每個工作中的對話每半秒檢查一次它的代理程式：向 AO 服務讀取代理的工作階段與最新對話內容，並向本機執行服務讀取該對話的執行。即使代理只是持續工作了好幾分鐘，也照樣每半秒讀一次。
  - 2026-11-10 實際觀察：九個對話同時工作時，每秒有 17 次執行讀取與 14 次工作階段讀取；本機執行服務與 AO 服務各佔約六分之一個 CPU 核心，App 主程序也再佔約六分之一。
  - 現在代理只是在工作的對話，每 1.5 秒檢查一次；等待你回應（工具核准或提問）、正在啟動，或有排隊訊息的對話，仍每半秒檢查一次。你在 App 中的操作（追問、重試、停止）一樣立即生效。
  - 唯一可能察覺的差別：回合結束或新的工具請求，最多晚約一秒出現；你看到的即時回覆串流不受影響。

### 修正：結束程式不再在資料資料夾留下暫存檔（#1187）
- **每次結束程式都會留下一個 `window-state.json.tmp-*` 檔案**，到 2026-11-10 已累積 50 個。
  - 程式結束時會儲存視窗位置，接著又開始第二次儲存同樣的位置。
  - 程式在第二次儲存完成前就結束了，來不及刪除暫存檔。
- **現在結束時只儲存一次。** 只有在先前的儲存仍在寫入時才會再存一次，避免較舊的位置最後寫入。
- **遺留的暫存檔會在下次啟動時移除**，在主執行緒之外進行；只移除這個檔案超過 10 分鐘的暫存檔。

### 對話：每個 harness 都顯示自己的圖示（#1188）
- **Harness 清單現在顯示每個代理程式真正的圖示。** 清單裡有許多標誌取自另一個應用程式的圖示集，並不是產品本身的圖示：
  - Claude Code 顯示像素吉祥物，Qwen Code 顯示阿里雲的標誌，Kimi 顯示 Moonshot 的條紋球，Grok Build 顯示一個無關的「xI」。
  - Gemini CLI 顯示 Gemini 模型的星芒，Amp 顯示舊的箭頭標誌，Pi 顯示一個塗鴉，Muse Code 顯示米色迷宮。
  - opencode、Cline、Cursor 與 Kilo Code 只有淡灰色的外框。
  - 現在每個都顯示其官方網站或程式庫使用的圖示：Claude Code 深色底上的橘色星芒、Qwen 的星形、Kimi 的「K」、Grok Build 的 SpaceXAI 標誌、Gemini CLI 的「>」圖塊、Amp 的圖塊、Pi 的像素 P、Muse Code 使用 Meta 的標誌，以及 opencode、Cline、Cursor 與 Kilo Code 各自的圖示。
  - 其他 harness 原本就是自己的圖示，保持不變。
- 黑色圖示（Cline、Grok Build）在深色主題中會變成白色。Kimi 的黑色「K」保留淺色底。

### 對話：在後面的對話分頁上操作會留在該分頁（#1189）
- **在第 2 頁或之後的分頁開啟對話時，會跳回較前面的分頁。** 在側邊欄選取對話、從「結構」或其他專案開啟對話，以及分割檢視的操作，都會回到該對話先前所在的分頁。
- **現在都會在你正在看的分頁上開啟。** 該分頁上的其他窗格保持不變，同一個對話也不會同時出現在兩個地方。
- 若對話無法在該處開啟，分頁會顯示「This chat could not be opened on this page.」，而不會把你移到其他地方。

### 修正：凍結後立即輸入的訊息不再被當成「視窗未聚焦」而拒絕（#1191）
- **程式凍結一段時間後，送出訊息可能失敗**，顯示「Click into the Coding Tools window and try again」，即使訊息是在視窗中輸入的。2026-11-10 在 17 至 36 秒的凍結後立即發生了兩次。
  - 程式從凍結中恢復時，會在收到訊息之後才得知視窗已被點擊，因而以為視窗不在前景。
- **現在從顯示中的視窗送出時，最多會等待 2 秒**讓視窗的聚焦生效，再決定是否拒絕。最小化或隱藏的視窗，或始終沒有聚焦的視窗，仍會立即被拒絕。

### 速度：本機執行服務每次請求的磁碟工作大幅減少（#1192）
- **App 對本機執行服務的每次請求，碰觸磁碟的次數約只剩原來的五分之一。**
  - 這個服務把設定存在一個資料檔中。每次讀取前，它都會重新查找並解析自己資料夾的路徑；在這台電腦上，該資料夾是從 C: 連結到 G: 的連結，因此每次查找需要 17 次檔案系統呼叫，而每次讀取還要查兩次。它每次也會重新建立那個早已存在的資料夾。
  - 2026-11-10 實際觀察：九個對話同時工作時，每半秒約 2,000 次檔案系統呼叫（每個請求約 240 次），該服務佔約六分之一個 CPU 核心。
  - 現在資料夾路徑只解析一次並記住，資料夾也只在不存在時才建立。讀取一次資料檔，從 57 次檔案系統呼叫降到 12 次。

### 修正：Chrome 登入不再搶走另一張卡片的 ChatGPT 帳號（#1193）
- **Chrome 可以同時登入兩個 ChatGPT 帳號**（ChatGPT 的帳號切換功能）。Chrome 連接器會複製這個設定檔完整的 ChatGPT 登入狀態。
  - 複製過來的工作階段可能開成*另一個*帳號，而不是 Chrome 當時顯示的那個。
  - 如果那個帳號已是「ChatGPT 瀏覽器管理」中的另一張卡片，新卡片就會用上它的電子郵件。結果兩張卡片顯示同一個帳號，新的那張顯示「尚未檢查」。
- **現在匯入時會先確認拿到的是哪個帳號，再交給卡片。**
  - 連接器（1.1.0）會告訴程式 Chrome 頁面登入的是哪個帳號。
  - 如果複製的工作階段開成另一個帳號，或開成另一張卡片已有的帳號，程式會拒絕這次登入；無法確認帳號時也會拒絕。
  - 被拒絕的登入會從該卡片清除。訊息會說明是哪個帳號、哪張卡片已有它，以及該怎麼做：在 Chrome 的 ChatGPT 帳號選單登出另一個帳號，或改用只登入目標帳號的 Chrome 設定檔，然後重新連接。
  - 卡片的電子郵件與 MCP 設定會等這項檢查完成，所以被拒絕的登入不會留下任何東西。
- **已經重複的卡片會保留，直到你移除它。** 在顯示「尚未檢查」的卡片上按「移除」，再重新加入帳號。
- 已安裝的 Chrome 連接器要等 Chrome 重新載入（重新啟動 Chrome）才會更新到 1.1.0。在那之前，程式仍會拒絕另一張卡片的帳號，但無法與 Chrome 顯示的帳號比對。

### CPA：額度帳戶跟隨目前的 CPA 連線（#1195）
- **CPA 斷線，或其位址或管理金鑰變更後，對話的額度清單可能在最多 20 秒內仍顯示舊連線的帳戶。**
  - 新連線也可能等待舊連線仍在進行的讀取。
  - 舊連線較晚完成的更新可能清空新連線的清單。
- **現在每次額度讀取都屬於一個 CPA 連線**（其位址與管理金鑰）。
  - 斷線時會丟棄舊連線讀到的內容。
  - 連線變更後才完成的讀取，會回報額度無法取得，而不會顯示舊帳戶。
  - 連線未變更時，讀取仍共用請求與短期快取。

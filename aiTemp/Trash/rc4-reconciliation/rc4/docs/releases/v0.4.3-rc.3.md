# v0.4.3-rc.3 — OAuth popup and callback repair / OAuth 彈出視窗及回呼修正

## English

This Windows release packages the previously unreleased ChatGPT-origin fix with a narrower boundary than main commit `07faa97`, and fixes a second browser-side callback blocker. Refreshing ChatGPT cannot update the installed `v0.4.3-rc.2` executable.

The HTTP guard accepts the exact HTTPS origins `https://chatgpt.com`, `https://chat.openai.com` and `https://www.chatgpt.com` only for GET/POST `/oauth/authorize`. It no longer trusts an arbitrary matching Host/Origin pair. Host, Forwarded and X-Forwarded-Host cannot nominate a trusted origin or OAuth issuer. Ordinary MCP, Actions, metadata and token endpoints retain their existing origin policy. Protected tools still require authentication.

A real Chrome 152 probe reproduced the second blocker: `form-action 'self'` lets the login POST reach the server, but blocks the resulting cross-origin OAuth callback. Validated authorization pages now allow exactly the validated callback's origin in their form CSP, in addition to self. A private response marker preserves that policy through the outer middleware; request headers cannot create it. Scripts, framing, base-URL changes and unrelated destinations remain blocked. Invalid callback requests do not acquire a permissive CSP. The successful callback is still HTTP 303, so the browser follows it with GET and does not forward the password body.

Opening the page does not grant access. Client/redirect checks, PKCE, password, request-bound consent nonce/cookie, one-use authorization code and token validation remain in place. Desktop-managed tunnel changes update the trusted origin used by the existing listener; this does not update the endpoint saved in ChatGPT. A changed Quick Tunnel URL can still require updating the client connection. The application cannot silently register or reauthorize a ChatGPT account.

Verification first reproduces rc.2 popup rejection and main's overbroad Host/origin acceptance. Four focused Windows tests then cover the corrected guard and the actual local HTTP consent-to-token-to-catalog flow, including state/cookie tampering, one-use codes, all 70 definitions, validated callback CSP and trusted origin rotation without restarting the listener. A separate real Chromium popup check replays the exact production HTML/headers and a sanitized production redirect: the old policy blocks, the corrected callback completes as GET without a password body, and an unrelated callback destination remains blocked. Browser transport is intercepted; no live ChatGPT account or Cloudflare service is contacted. Existing catalog/transport regressions, frontend build and installer-byte inspection also gate publication. No Codex executable or model inference is invoked.

Install this version and restart the desktop application once, then retry Connect from the existing ChatGPT connection using the application's current HTTPS `/mcp` URL. Complete the normal consent/password flow. Do not strip query parameters, erase OAuth state, disable origin checks or raise execution permissions to fix login. If authentication succeeds but tools are missing, use Advanced/Full and Tool exposure diagnostics, then refresh the client's saved tool metadata as needed. Permission-only changes still need no MCP restart or relink.

A popup without an address bar does not reveal which HTTP headers were sent. The reported Origin failure was reproduced for requests carrying that Origin; the user's actual popup headers, present tunnel reachability and installed H: executable were not inspected. These tests are not live-account acceptance or a comprehensive security certificate.

The previous catalog, model-free native commands, RAM-only screenshots and remembered computer controls are retained. The broader sandbox/file audit remains separate and unfinished; `sandbox_exec` stays unavailable. This is not complete Codex internal-tool parity. Windows is publisher-unsigned. Existing releases, files and credentials are preserved.

## 繁體中文

本次 Windows 版本將之前只存在原始碼的 ChatGPT 來源修正打包，收窄 main Commit `07faa97` 的信任範圍，並修復第二個瀏覽器回呼阻礙。刷新 ChatGPT 不會更新已安裝的 `v0.4.3-rc.2` 執行檔。

HTTP 檢查只在 GET／POST `/oauth/authorize` 接受精確的 HTTPS 來源 `https://chatgpt.com`、`https://chat.openai.com` 及 `https://www.chatgpt.com`。不再因任意 Host／Origin 相符就視為可信；Host、Forwarded 及 X-Forwarded-Host 不能自行指定可信來源或 OAuth 發行者。一般 MCP、Actions、中繼資料及 Token 端點保留既有來源規則，受保護工具仍須認證。

真正的 Chrome 152 測試重現第二個阻礙：`form-action 'self'` 讓登入 POST 到達服務端，卻阻擋其後跨來源的 OAuth 回呼。已驗證的授權頁面，現只在表單 CSP 額外允許該已驗證回呼的來源；其他情況仍只允許自身。私有的回應標記讓外層 Middleware 保留此規則，請求標頭不能偽造該標記。腳本、嵌入頁面、基底網址變更及無關目的地仍被封鎖；無效回呼請求不會取得較寬鬆的 CSP。成功回呼仍使用 HTTP 303，瀏覽器以 GET 跟隨，不會轉發密碼表單內容。

開啟頁面不代表已獲授權。Client／Redirect 檢查、PKCE、密碼、綁定原請求的同意 Nonce／Cookie、單次授權碼及 Token 驗證均保留。桌面程式管理的隧道變更會更新既有監聽服務的可信來源，但不會更新 ChatGPT 已存端點。Quick Tunnel 換網址後仍可能需要更新用戶端連接，程式不能靜默替 ChatGPT 帳戶註冊或重新授權。

驗證先重現 rc.2 的來源拒絕及 main 過於寬鬆的 Host／Origin 接受。四項 Windows 重點測試再涵蓋修正後的來源檢查及真正本機 HTTP 同意、Token、工具目錄流程，包括 State／Cookie 竄改、授權碼單次使用、全部 70 個定義、已驗證回呼的 CSP，以及不重啟監聽服務的可信來源輪換。另外使用真正 Chromium 彈出視窗，重播正式程式產生的 HTML／標頭及已移除真實測試授權碼的跳轉：舊規則會阻擋、修正版以 GET 完成回呼而不轉發密碼、無關回呼目的地仍被阻擋。瀏覽器傳輸由測試攔截，不接觸真實 ChatGPT 帳戶或 Cloudflare。既有目錄／傳輸回歸、前端建置及安裝包位元組檢查亦是發佈關卡；不啟動 Codex 執行檔或模型推論。

安裝後重新啟動桌面程式一次，再使用程式目前顯示的 HTTPS `/mcp` 網址，從既有 ChatGPT 連接重試 Connect，照常完成同意／密碼流程。不要刪除查詢參數、清空 OAuth 狀態、停用來源檢查或提高執行權限來修復登入。若認證成功後仍缺工具，使用 Advanced／Full 及 Tool exposure 診斷，並按需要刷新用戶端已存工具資料。只修改權限仍不必重啟或重新連接 MCP。

沒有網址列的彈出視窗外觀，不能證明實際發出了哪些 HTTP 標頭。本次可重現带有所述 Origin 的拒絕，但未檢查使用者真實彈出視窗標頭、目前隧道連通性或 H: 上已安裝的執行檔。這些測試不代表真實帳戶驗收或全面安全認證。

之前的工具目錄、免模型原生命令、記憶體截圖及已記住的電腦控制均保留。較廣泛的沙箱／檔案稽核仍獨立保留、尚未完成；`sandbox_exec` 繼續不可用。本版不是完整 Codex 內部工具對等實作。Windows 沒有發佈者簽署；既有 Release、檔案及憑證均保留。
